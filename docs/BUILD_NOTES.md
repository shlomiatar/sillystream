# Build notes

Choices made where `docs/SPEC.md` is silent or ambiguous, and questions for the user. SPEC.md stays the source of truth: nothing here changes its meaning, and any item can be reversed. Each entry is one choice and its reason. Later milestones append here.

## Questions for the user

Each has a working assumption so the build can continue.

- **Q1. No `to` on subscribe.** Section 4 says an id range "from any point to any point", but `SUBSCRIBE` and HTTP `read` carry only a start (`from`, plus `limit`). Assumption: no new field; the client stops at its end id.
- **Q2. No admin API.** Sections 9, 12 and 13 require stream create, config, delete and the sink lifecycle under `admin`, but section 11 has no route for them. Assumption: the smallest HTTP additions, listed in D21.
- **Q3. Manifest record type.** Section 7.5 publishes seal manifests to a system stream, and only `author = 0` data may be read by the server, but section 2.2 defines entry types 1–3 only. Assumption: manifests are system records with entry type 4 in a stream named `_sys.manifests`.
- **Q4. Manifest stream's special rule.** Section 7.5 says one is needed but not what it is. Assumption: manifest stream segments are never listed in a manifest and never compacted; they stay in `sealed/`, and the delete job's compaction check covers them.
- **Q5. "One preallocated file" versus recycling.** Section 6.3 has one file, but entries covering a sealed-but-not-yet-uploaded window must survive while new ones arrive, and old entries in a recycled file still have valid CRCs. Assumption: D8.
- **Q6. One "last valid id" with per-stream ids.** Section 8.1 keeps a single id, but ids are per stream. It works because ids are time-based: it is the highest id seen at takeover, and every new id on every stream is above it (D15). An old generation's object at or below that id is accepted. Please confirm.
- **Q7. Lost records at levels 0–1 and id reuse.** A record delivered at level 0–1 and lost in a crash leaves no trace, so "ids are never reused" cannot be proven for it. A restart normally moves past it because ids follow the clock; a backward clock or borrowed ms could collide. Assumption: the no-reuse guarantee is tested for WAL-durable records only.
- **Q8. Checkpoint lookup and cleanup.** *(Answered in code by D18, D139 and D147: walk, with periodic full files, and only a startup deletes. Still an assumption until you confirm. D147's cost is that a node's checkpoint files pile up until its next restart: is that acceptable, or should a running node clean up too, at the price of a small race?)* Section 7.6 puts checkpoints in shared files per seal, but does not say how a long-idle stream finds its latest one, or whether old files may be deleted ("nothing else deletes data" is about records). Assumption: D18.
- **Q9. Upload outage.** The spec doesn't bound memory and WAL while S3 is down. Assumption: slabs and the WAL stay pinned, and when a configured cap is reached it becomes publisher backpressure (D7). Level 3 acks wait.
- **Q11. `eq` value bits outside the mask.** Section 4 defines `eq` as `(options & mask) == value`, which is never true if `value` has bits outside `mask`, but the formula in section 4.1 uses `need1 = mask & value` and would report "all match" for such a clause. Assumption: section 4's definition wins (D33).
- **Q12. `ACK.count` is a u32.** A maximum-size frame can hold about 500,000 empty records of 65,535 items, around 3.4 × 10^10 items, which `ACK.count` can't express. Section 3's rejection list doesn't cover it. Assumption: D34.
- **Q13. Nothing bounds how far ids can run ahead of the clock.** Section 2 says the id is the item's timestamp and that the owner borrows the next ms when counter values run out, with no limit. The server can't check `count` against the data, and section 3's rejection list allows `len = 0` with `count = 65,535`, so 32 bytes buys about 1 ms. One 2,097,184-byte publish of 65,537 such records moves a stream about 65.5 s ahead, 1,000 of them about 18.2 hours, and sustained 1 GB/s about 8.7 hours per second. Every later record on that stream, from any producer, then gets a future timestamp until the clock catches up. Order stays strict, so this isn't an ordering bug. By reading only, since those layers aren't built: id-range time filters, retention by ingest time (section 7.4) and `sealed/<ingest_hour>` paths would use the skewed time, and under Q6/D15 the highest id at takeover raises the floor for every stream on the node, so one publisher could skew other streams after a restart. Rejecting `len = 0` with `count > 1` only raises the price, since a few data bytes pass, and it would contradict the `max_count.hex` vector. Options: reject a publish that would put ids more than a set margin ahead of the clock (error 8, or backpressure), or limit items per second per stream. Assumption: no bound, because adding one is a new mechanism and the margin is a product choice. **Not fixed.** `q13_empty_max_count_records_move_ids_ahead_of_the_clock_without_bound` in `crates/format/tests/ids.rs` pins the behaviour and changes with the decision.
- **Q10. Conditional update on the ownership record.** "One ownership record" with a conditional increment needs compare-and-swap, which `object_store`'s `LocalFileSystem` doesn't implement (`PutMode::Update` returns `NotImplemented`; checked in 0.11.2). Assumption: D14.
- **Q14. A stream id ending in `*` can't be granted exactly.** Section 1 allows any UTF-8 name without `/`, so `team*` is a legal id, but a trailing `*` in a pattern is always a wildcard (D25, D46) and a pattern has no literal form. An issuer granting exactly `team*`, or building `inbox.<user>` from a user-chosen name of `*`, also grants `teamsecret` or every `inbox.` stream, with no error at sign or verify. That widens access against section 12's "anything private goes in its own stream". Options: forbid a trailing `*` in stream ids (narrows section 1), or add an escape to patterns (a new mechanism and a token format change). Until then an issuer that builds patterns from user input must refuse a trailing `*` itself. Assumption: no change, because both options change the spec's meaning. **Not fixed.** `q14_a_grant_on_a_stream_id_ending_in_star_is_a_prefix_grant` in `crates/auth/tests/token.rs` pins the behaviour and changes with the decision.
- **Q15. Bit rot in a closed WAL file can't be told from its normal end.** A closed file ends in zeros or in stale entries of a reused file, and a corrupt entry looks the same, so replay takes each file's valid prefix and goes on to the next (D8 has no end marker). A flipped bit in the middle of a closed, not yet recycled file silently drops that file's later entries, while later files replay, which can leave a gap inside a stream. A torn tail in the active file, the case the CRC is for, is unaffected. Options: a final entry marking a clean close, or the closed length in the next file's header, both new mechanisms. Assumption: leave it, since a closed file is needed only if the machine crashes before its segment is uploaded. **Not fixed.** `a_directory_replays_oldest_first_and_ignores_other_files` covers the walk, and no test claims detection.
- **Q16. Object paths can collide.** Section 7.3's path holds `<node-or-stream>`, so a stream named like the node shares a directory with it, and `first_id` isn't unique across streams, so two objects can in principle want one path, most easily with ids borrowed ahead (Q13). Assumption: the uploader never overwrites. Identical bytes count as done, and different bytes fail that upload and hand its references back (D55), which is safe but leaves those records unuploaded until someone acts. Options: reserve a prefix for one of the two, or add something unique to the file name. Please choose.
- **Q17. A per-object failure the uploader can't recognise still stalls it.** D59 fails an upload whose path can't exist, or whose store error says retrying is pointless. Every other error retries forever on the one thread (D55), because it can't be told from an outage: `LocalFileSystem` reports most I/O failures as `Generic`, and real S3 was not exercised, so its responses aren't known. If some store rejected one object deterministically with such an error, every later upload on the node would wait behind it. Options: move retries off the head of the queue (needs its own bound to keep backpressure), or cap attempts (can't be told from a long outage). Assumption: leave it, since no such case is known. **Not fixed.**
- **Q20. Can a snapshot show state that isn't durable yet?** Section 10 says a change "goes into the WAL, is applied in RAM, and is then acked", and section 5.2 holds delivery until the WAL, but says nothing of a snapshot. `expect_ver` has to see earlier changes as soon as they are stamped, so they are applied at once, and a snapshot taken during the fsync can return a version that a crash then erases. A lease holder could see a version that later doesn't exist. Options: a snapshot waits until the stream's last ticket is durable (it would hang on a held WAL, and the snapshot would be slower), or leave it. Assumption: it doesn't wait. **Not fixed.**
- **Q21. What does a stream's own record of moves cost over time?** A stream carries `(last_id, core)` per move, so a retry can find the core that stamped it (D67), and each core keeps its override entries and old shard locations for good (D66). Nothing trims them. Moves are few, so this is small, but it's unbounded on a node that lives long and rebalances often. M7's metadata is the natural place to prune history older than the sealed extent. Assumption: leave it for M7. **Not fixed.** M7 didn't prune it either: a stream's move record is rebuilt empty by a reload, which only retries of a publish from before the reload could notice, and those are answered by the saved dedupe table.
- **Q18. Who enforces the segment size cap?** Now assumed answered by D64: each core asks for a seal at its share. Please confirm.
  Original question:  Section 7.3 writes a segment every seal window "or earlier when the size cap is reached (32–128 MB)". Nothing enforces or names a cap: `build_seal` and `SegmentBuilder` accept any size, and `docs/BENCH.md` records a 1,000,000-stream object of 221 MiB. One object per seal is built from sections sent by N independent cores, so no core can see the object's total, and the uploader only sees it after every core has sealed, too late to seal "earlier". Options: each core seals early on its own share of the cap and tells the others by message, as part of M4's seal logic; or the uploader splits a completed seal into several objects, which breaks one PUT per seal and only bounds the object, not the window. Assumption: M4 owns this (noted in its scope in `docs/BUILD_PLAN.md`), and until then there is no cap. **Not fixed**, and there is no regression test, because what to test depends on the choice.
- **Q19. Nothing bounds a PUT while the uploader runs normally.** `shutdown` now abandons a PUT that doesn't return, but `finish`, and every upload behind a hung PUT, still wait for it. `build_store` sets no client timeouts, so S3 relies on `object_store`'s defaults, whose behaviour in an outage wasn't measured because real S3 was not exercised. A stalled `LocalFileSystem` mount has no bound at all. Options: a per-attempt timeout that counts as a retryable failure; its value is a product choice, and for large objects it must allow for the upload's length. Assumption: no timeout. **Not fixed.**

- **Q23. What is `STATE` for, and what do `WITH_STATE` and `STATE_ONLY` mean exactly?** Section 11.1 lists the frame and flags and nothing says when they apply. Assumption: D88.
- **Q24. Does a subscription carry on by itself after `BEHIND`?** Section 5.2 says it "gets `BEHIND {resume_from}` and falls back to catching up", which could also mean the client resubscribes. Assumption: the server carries on by itself on the same subscription, and a client that resubscribes from `resume_from` also gets everything (D86).
- **Q25. Subscribing to a stream that doesn't exist.** Section 13 creates streams on publish or state write only, and section 11.1 has error 2. Assumption: error 2, as a snapshot does (D71), so an agent that subscribes before anyone publishes has to retry or create it first. A subscribe that waits would be a new mechanism. Please confirm, since this may not be what agents want.
- **Q26. How exact is "before the start of retention"?** Nothing deletes records until M8 and extents aren't kept per record. Assumption: D89, which can't see inside an extent holding the cursor, and then lets the read go ahead, for a cursor within one seal window of the boundary.
- **Q27. Is one lock per connection acceptable?** D99 has a mutex between a home core and that connection's reader, which is the one thing here that isn't a message. No two cores ever hold it. M6's socket writer lives on the home core and could drop it. Options: keep it, or a per-frame cell, which allocates per frame and still needs one. Assumption: keep it.
- **Q28. How stalled is stalled?** D99 calls a connection stalled if frames wait through a whole check, 50 ms, with none taken, and only looks while slabs are at 3/4 of the cap. Section 5.2 has no such number. Assumption: those values, as constants.
- **Q22. No error code for a dead WAL.** Section 11.1 has none that fits, and a new code would be a new concept. Assumption: code 4 (rate limited) with the message saying what happened, since backing off and retrying with the same producer seq after a restart is the right client action (D79). A dedicated code would let clients fail over without reading the message.
- **Q29. Where does a named cursor start inside a record?** Section 5.2 has the client skip ahead by id, but `SUBSCRIBED` doesn't tell a client the position of its named cursor, so a commit that stops inside a record repeats that record's earlier items on the next subscribe. Assumption: that is section 5.1's at-least-once, and the SDK skips by id only from a `from` it knows and what it has handed over itself.
- **Q30. What does a `NACK` of error 4 mean for a pipelined producer?** Section 3 says a later seq succeeding makes a retry look like a duplicate, and only `expect_ver` publishes hold later ones back. Assumption: the SDK doesn't retry a `NACK`, returns it to the caller, and a caller's retry is a new seq. So a rate-limited pipelined publish can land behind later ones if the caller retries it.

## Decisions

### Format and frames

- **D1.** `op` in filter clauses: 0 = `eq`, 1 = `any`. Reason: the spec gives the field but no codes.
- **D2.** `nfilt = 0` matches every record; `nfilt > 4` is error 8. Reason: follows "up to 4 clauses".
- **D3.** App filters (`options`, `author`) don't apply to system records; `INCLUDE_SYSTEM` delivers them all. Block skipping for such a reader is allowed only when the block's `author` is a non-zero value. Reason: on system records `options` is the entry type, so a block could otherwise be skipped while holding one.
- **D4.** `SDK from`: the client sends `from = head` after a snapshot. Reason: section 10 says "read from `head + 1`", and section 5.1 defines `from` as "after this id", so they agree only this way.
- **D5.** A publish with `HAS_STATE` places the system record last. `ACK.first_id` is the first id of the publish and `ACK.count` counts all its items, including the system record. Reason: `first_id + i` then still maps to the producer's items.
- **D6.** `producer_id = 0` means no idempotency: it is what `STATE_OP` and HTTP publishes without the headers use, and it creates no dedupe entry. Reason: the WAL entry always has the field, and `expect_ver` covers state retries.
- **D6a.** Level 0 sends no `ACK`, but a rejection still gets a `NACK`. A publish below a stream's minimum ack level is raised to it. A publish with neither records nor state is error 8. A state result over 64 KB is error 8. Reason: smallest reading of sections 3 and 13.
- **D6b.** `STATE_RESULT` carries `ok = 0` only for a version conflict; other failures send `ERROR` with `ref = req`. Reason: `STATE_RESULT` has no code field.
- **D6c.** Merge is RFC 7396 semantics on CBOR maps. Incr's doc is CBOR `{"path": [keys], "n": int}`. Incr on a non-numeric value is error 8. Reason: the spec names the ops but not incr's doc.
- **D6d.** Defaults: `max_frame` 16 MiB, subscriptions per connection 1,024, subscriber queue 8 MiB, `PROGRESS` every 5 s, slab 4 MiB, block 64 KiB, footer page 64 KiB. Reason: plain starting values; all are constants or node config.
- **D6e.** Dedupe's 28 bytes are `producer_id, producer_seq, first_id, count`, and idle age comes from `first_id`'s timestamp. Reason: the id already holds the time, so no field is added.
- **D33.** An `eq` clause with `value & !mask != 0` matches nothing, and its block decision is "none match". Reason: keeps sections 4 and 4.1 consistent (Q11).
- **D34.** A publish with more than `u32::MAX` items is rejected with error 8. Reason: `ACK.count` couldn't report it (Q12).
- **D35.** A block summary's `count` is items, and `bytes` is whole records including headers and padding. The summary's on-disk layout is left to M3 (D10). Reason: the spec names the fields only; items match the id range, and whole-record bytes are what a reader fetches.
- **D36.** The allocator never issues `u64::MAX` and refuses an allocation that would need it. Id 0 is never issued either. A clock above 48 bits is clamped. Reason: section 5.1 gives both values cursor meanings, and `first_id = 0` means "already committed" in an `ACK`.
- **D37.** A record overlapping a filter's id range matches whole, and the decoder rejects non-zero padding as well as validation does. Reason: section 5.2 sends whole records; padding isn't data, and nothing valid has non-zero padding.
- **D38.** `validate_forward` requires a non-zero `author`, and `id = 0`, for records from a forward sink. Reason: section 3 lets forward sinks set `author`, and D28 keeps system records out.
- **D39.** Frame decoders are strict: unknown types, undefined flag bits (flags must be 0 on frames that define none), trailing bytes, `ack` above 3, a state `op` outside 1–3, `ok` above 1 and error codes outside 1–8 are errors. Reason: each frame then has one encoding, and section 3 and 11.1 define no other values.
- **D40.** A token's text form is the lowercase hex of D25's bytes. Reason: `HELLO` carries `token str`, which must be UTF-8, and a Bearer header must be text, but D25's bytes are binary; hex needs no dependency, and one case means one text form.
- **D41.** `HELLO.ver` is 1 for now, and the codec doesn't check it. Reason: the spec gives the field but no value, and what to do on a mismatch belongs to the connection (M6).
- **D42.** A stream id in a frame must be non-empty as well as free of `/`, and the codec checks both. Reason: section 1 calls them names; a bad id fails as error 8 before reaching a core.
- **D43.** `max_frame` covers the whole frame, including `type` and `flags`. A frame above it is error 6, and every other decode failure is error 8. Reason: the WebSocket message length is what a reader can check first.
- **D44.** The codec accepts all 32 `SUBSCRIBE` flag combinations, including `WITH_STATE` with `STATE_ONLY`, and leaves their meaning to the subscribe handler (M5). It also doesn't check `sink:*` cursor names (D27), state doc size or CBOR, or record validity, which belong to the owner. Reason: these need context or are section 3's validation, and the codec never reads inside `records`.
- **D45.** Permission bits: `read` 0x01, `publish` 0x02, `state` 0x04, `admin` 0x08, and other bits make a token invalid. Reason: D25 gives `perms u8` but no bits.
- **D46.** A token is expired once `now_ms >= expiry_ms`. `*` is a wildcard only as a pattern's last character, and it matches an empty remainder, so `logs.*` matches `logs.` but neither `logs` nor `logsx`. A `*` elsewhere is an ordinary character. The signature is checked before the body is parsed. Reason: smallest reading of D25; unauthenticated bytes never reach the parser.
- **D47.** `Token::sign` and `verify` accept any secret length, including empty. Rejecting a weak secret is for node config, when it is added (M6). Reason: the token code has no policy on keys, and HMAC accepts any length.
- **D48.** Token text is at most 65,535 bytes, so 65,534 in practice because hex is even, and `body | signature` at most 32,767 bytes. `sign` and `verify` both return `TooLong` above it, on HTTP as well. An exact grant on a stream id over about 32.7 KB can't be issued, though such an id is valid (section 11), and has to use a shorter `*` pattern. Reason: `HELLO` carries the token as a `str`, and one limit means a token can't work on HTTP and always fail on WebSocket.
- **D49.** The `auth` crate is `no_std` plus `alloc`. A test refuses any opt back in to `std` in any `.rs` file under `src/` at any depth, source pulled in with `path` or `include`, a build script, and any manifest line outside a short allow list, which covers target-specific and table-form dependencies. Reason: it makes "verification does no I/O" a compile error instead of a source search that a nested import gets past. The check is a word scan, not a parser, so it is meant to catch mistakes and not a determined author; the two hash crates and their workspace entries are trusted.

### Storage

- **D7.** A core keeps a bounded outbound queue for when `try_send` fails and stops reading publish frames while it is non-empty or the memory cap is reached. Reason: backpressure without blocking a core or dropping a stamped record.
- **D8.** The WAL is a sequence of preallocated files, `wal-<seq>.log`, with one active at a time, rotated at seal, and renamed for reuse once its segment and checkpoint are durable. The first 16 bytes of each file are a magic and `seq`, and the entry CRC is seeded with `seq`. Reason: stale entries in a reused file fail the CRC, with no added entry field. The CRC isn't enough on its own, because it isn't authenticated: see D60.
- **D9.** WAL entry: `stream_len u16 | stream | producer_id u64 | producer_seq u64 | len u32 | crc32c u32`, then the record bytes padded to 8. One publish is one entry, so an atomic publish can't be torn apart. State ops are found by reading `author = 0` records during replay. Reason: the spec's fields in its order.
- **D10.** Segment layout: sections of stream extents, then footer pages sorted by `xxh3_64(stream)`, then the top index and a fixed trailer (`magic, top_offset, top_len, crc32c`). Each extent starts with a block summary table followed by blocks of whole records. Stream index entries hold the full name to resolve hash collisions. Reason: follows section 7.3; a reader's data step may take one read for the table and one for the blocks.
- **D11.** Unsealed records are served from memory, since slabs are pinned until upload. The local tier is a copy of the uploaded segment, under a byte cap. Reason: the WAL is read only during recovery.
- **D12.** The uploader is one thread with its own current-thread tokio runtime, used only for `object_store` calls. Reason: `object_store` is async, and the thread pattern is the spec's.
- **D13.** Extra node config beyond section 13: listen address, TLS cert and key, token secret, object store URL and credentials source, node name, `data_dir` (KV and local cache), local cache cap, memory cap, and `sink_allow_private_addresses` (default false). Reason: required to run; none changes behaviour the spec defines.
- **D50.** Every WAL entry starts at a multiple of 8 in its file, so the padding of D9 brings the whole entry, not just the records, to a multiple of 8. The CRC covers every entry byte except itself, padding included, and is seeded with `seq`. `stream_len = 0` and `len = 0` are invalid, which is what ends the prefix at a preallocated tail of zeros. Reason: padding is part of the entry, and no publish has an empty id or no records (D6a, D42).
- **D51.** Preallocation is `set_len`, which is sparse on APFS and on Linux filesystems. A write past the preallocated size just extends the file. Reused files keep their size (D60). Reason: real allocation needs `fallocate` or `F_PREALLOCATE`, so `unsafe` or a libc dependency, for a benefit nothing here has measured. A file's writes therefore may still allocate, and `sync_data` then also flushes that metadata.
- **D52.** Segment bytes are documented at the top of `crates/storage/src/segment_format.rs`. Three choices beyond D10. (1) A footer page's 64 KiB is a target, not an exact size, and pages aren't padded: a page holds all entries with one hash, however many, so a lookup is always one page read, and a stream id can be longer than a page. (2) A block is at most 64 KiB unless a single record is bigger. (3) The trailer has no fixed place for a reader to find the top index without knowing the object's size, so the first read is a 256 KiB suffix read, which holds the trailer and normally the whole top index (about 11,000 pages). A bigger top index takes a second read, and is tested. Reason: one read and no `HEAD`.
- **D53.** `ingest_hour` in an object path is whole hours since the epoch, from the object's lowest id. Generation and `first_id` are zero-padded to 20 digits. Each is one path part, so `object_store` encodes anything unsafe in a stream id. Reason: the spec names the parts but no form, and padded numbers list in order.
- **D54.** The local cache is one directory laid out as `LocalFileSystem` expects, so `SegmentReader` reads it as a store, and is owned by the uploader thread. Reads happen on cores through the file system, and tell the owner with a `try_send` that may be lost, on a queue of their own, so reads can't make a section come back `Full` and turn into publisher backpressure. Eviction is least recently used by bytes, and after a restart by modified time. Writes aren't fsynced. A failed write removes its temp file, and eviction removes directories it empties, as does opening. Reason: no lock is shared, CRCs catch a bad copy, and a miss falls through to S3.
- **D55.** A seal or dedicated object is written with one plain `PUT` using `PutMode::Create`, so S3 needs `S3ConditionalPut::ETagMatch`, which `build_store` sets. If the path already exists with the same bytes, an earlier attempt succeeded and its response was lost, so it counts as done. With different bytes the upload fails (Q16). Store errors retry forever with exponential backoff, keeping the references, except those in D59. `shutdown` stops retrying, abandons a PUT in progress and returns every reference as `UnfinishedUpload`. An abandoned PUT may still land, which is harmless: the same bytes count as done if uploaded again, and an object no extent refers to is ignored (D16). A PUT stuck on a blocking thread keeps that thread until the call returns, since it can't be cancelled; the thread ends with the process. A section from a core out of range, or with a seal number not above that core's last one, fails and comes back the same way, so a repeat is caught after its seal has uploaded too, and a seal gets one PUT. A core's seal numbers must therefore only go up. Reason: never lose a reference or overwrite a sealed object. Retrying forever is Q9's assumption.
- **D56.** A WAL entry carries the owner's `core` and a per-core `ticket`, and the writer reports each core's highest durable ticket through a `tokio::sync::watch`, which an awaiting core wakes on. `changed()` failing means the writer stopped. `records` is generic over `AsRef<[u8]>`, and so are the uploader's references, so that M4's slab references plug in with no copy. Rotation goes through the same channel as appends and returns `{closed_seq, new_seq}`, so for M4's seal: rotate first, then each core seals what it holds once it hears the result. Everything in a closed file was sent before that, and so is in some core's section, which makes `try_recycle(closed_seq)` safe once that seal's segment and checkpoint are durable (D16). A group is capped at the channel's capacity, so fast senders can't hold one group open. Reason: the smallest message set that lets the cores keep everything else.
- **D57.** `MetadataStore` keys and values are opaque bytes, and `apply` commits atomically and persists with `SyncData`. What a stream's metadata holds is M7's (section 7.6). A key must be 1 to 65,535 bytes (Fjall's limit) and a value at most 2^32 - 1 bytes; anything else returns `MetadataError` before anything is applied, and a longer prefix scans as nothing. A stream id may itself be 65,535 bytes (section 11.1), so M7 can't simply add a prefix to one: such a stream would get the error. Reason: the fields' encoding has no user before M7, and Fjall panics on these inputs.
- **D58.** The uploader's channel and the dedicated-object decision: a core decides when a stream has filled its buffer and calls `try_send_dedicated`, because the buffer belongs to the core (M4). Each core sends one section per seal, empty if it has nothing, so the uploader knows when a seal is complete. A seal with no records writes nothing and reports `Empty`. Reason: section 6.4 has per-core hand-offs and one PUT per seal, which needs a count.
- **D59.** A path part may be at most 255 bytes as encoded (`MAX_PATH_PART_BYTES`), on every store, and a stream id that exceeds it can't have a dedicated object. The uploader reports `Failed` without trying, and keeps the references as in D55, so later uploads aren't held up. A core must check `stream_fits_dedicated_path` and keep such a stream in its seal sections, where the id is only in the footer and any length works, so section 1 still has no length limit. A node name over the limit fails every seal the same way. `InvalidPath`, `NotSupported` and `NotImplemented` store errors also fail at once rather than retrying (D55 still retries everything else; see Q17). Reason: 255 is the file name limit of common file systems, and one limit means a stream behaves the same on S3 as in a local test.
- **D60.** Reusing a WAL file empties it first: `set_len(0)` and `sync_all` under the old name, then the rename, then `set_len` back to its old size and the header. Entries in a closed file are already uploaded (D16), so nothing is lost at any crash point, and an empty file replays as no entries. Reason: record data is written verbatim and a seeded CRC isn't authenticated, so a publisher could plant a valid entry for a predictable future `seq`, with any stream, ids and `author = 0`, and replay would walk into it if new entries ended at that offset. Nothing at the entry level can reject those bytes, so they must not exist. An unpredictable per-file seed would stop guessing but change the file format, and writing zeros is O(file size) for the same result. Cost: a reused file no longer has allocated blocks, so its writes allocate as a new file's do (D51), and reuse now saves little beyond the create. Not measured: `wal_throughput` doesn't rotate, so docs/BENCH.md's numbers aren't affected. If reuse turns out not to be worth keeping, removing it is a separate choice.
- **D61.** Every uploader send is `sending_count += 1`, a check of the stop flag, the `try_send`, then `sending_count -= 1`, all sequentially consistent. After a stop, the uploader thread sees the count reach 0 and only then drains the channel. Reason: a command accepted with `Ok` while the thread was finishing was otherwise dropped with the receiver, against D55, and a sender that never paused kept the drain from ending. Sends happen per seal, not per record, so these shared atomics are off the hot path, and no sender ever waits. Only the uploader thread waits, for the length of one `try_send`.
- **D62.** A core retries a full WAL or uploader channel on a 1 ms timer while something is waiting. Reason: crossbeam gives nothing to await, and the writer's wake-ups only cover the core's own entries, while the channel can be full of other cores' entries.
- **D63.** An atomic publish or state op copies the stamped records and system record into one new slab region of the owning core, since one WAL entry holds one reference. A plain publish is never copied after it is read. Reason: the doc comes before the records on the wire, so the frame can't hold the system record where it belongs without the frame reader knowing; the cost falls only on publishes with state.
- **D64.** Each core sends the control thread a seal request when its unsealed bytes reach `segment_cap_bytes / core_count` (default 64 MiB, the middle of section 7.3's range), and one seal starts for the node (Q18). The bound is soft: bytes arriving before the seal reaches a core land in it, and one busy core seals at its share, not at the total. Reason: a core can't see the others' bytes, and this keeps one PUT per seal.
- **D65.** A publish carries no route. A core that doesn't own the stream forwards it, and tells the client `Moved`. The client keeps its route per stream until a barrier sent down the old route comes back from the owner (`RouteDone`), and only then sends directly. While a barrier is out, writes to that stream wait for it, and `try_publish` says `Full`, because a write sent behind the barrier could be overtaken after the switch and then be acked as an older duplicate without ever committing. The wait is one trip through the cores per move, or as long as the old core has stopped reading writes (D7), which is backpressure. Forwarded writes use an unbounded inbox, so two cores forwarding to each other can't wait on each other; what is in it has already been read from a bounded inbox. Reason: a publish sent on the new route could otherwise overtake one still being forwarded, and the older one would look like a duplicate and be dropped. No core or client needs a current routing table for this to be correct. This holds across a move back only with D78.
- **D66.** Each core's own map of `shard → where it last knew it was` is enough to reach an owner, because every core that gives a shard away remembers where it went. A stream's override entry is kept by every core that has owned its shard or its own shard, and a hashed shard's owner passes on entries for streams that hash to it. A handoff's location for an override shard is taken only by a core with no entry for that shard. A core's own entry stays, since it may have held the shard since the sender last heard. So each hop leads to a later holder of the shard, and the walk can't cycle or make a second owner. The control thread alone has the complete table, updated when a move finishes. Reason: a core acts only on what messages told it, with no shared table.
- **D67.** A retry waits for what it duplicates to reach the level it asks for. An older retry waits on the producer's latest publish, which came after it. If another core stamped those ids, it gets the wait as a message, using the `(last_id, core)` list the stream carries. A batch no longer held counts as uploaded. Reason: section 3 says the original `ACK`, and invariant 3 says never before the level is met.
- **D68.** A stream's unsealed batches and the acks waiting on them stay on the core that stamped them when it moves: its section covers them, which is how the seal gets its two footer entries. A seal takes one stay on a core per stream, so that a stream moving away and back in one window can't produce an extent overlapping another core's. The later stay waits for the next seal. `read_memory` reads one core's batches only. Catch-up reads across cores: D83.
- **D69.** Level 3 acks when the object holding the batch is uploaded, and doesn't also wait for its fsync: an entry sent between the rotation and the core hearing about it can reach the store first, and then S3 holds it, which is stronger. A seal takes only batches the WAL channel has accepted, so nothing reaches S3 ahead of an entry still queued on the core. An upload that fails for good (D55, D59) leaves its level 3 acks unsent, and is counted in `CoreStats`.
- **D70.** `STATE_OP` has no `ack` field, so it uses the stream's default level, and never less than level 2, including on a stream whose default is 0 or 1. Reason: section 10 says a change goes into the WAL and is then acked, with no level, and a client that sent no level didn't ask for memory-only. A publish carrying a state change has its own `ack`, so it follows that.
- **D71.** A rejected publish creates no stream. A stream is created when a publish or state write is accepted, or by `configure`. An id space exhausted on a new stream (only possible with a floor near `u64::MAX`) leaves it empty. A snapshot of a missing stream is error 2.
- **D72.** Node defaults: 4,096 virtual shards, 64 override shards, a dedicated object at 32 MiB unsealed, an overload ratio of 1.25 × the mean, 16 moves per check, a check every 10 s, 1,024 writes per inbox. A shard's load is its ingest, fan-out and catch-up bytes as moving averages with weight 0.5 per check; subscribers are counted but not weighed. A move takes the largest shard smaller than the gap to the coldest core, so a single huge shard stays put, and it takes the override table to split it. Fan-out, subscriber and catch-up counters are fed by M5's delivery. Reason: plain starting values.
- **D73.** The memory cap (D7) is checked in `Client::publish`, as the analogue of a connection not reading its socket, against the slabs of the client's home core. A core's own copies (D63) aren't limited by it. It should sit well above the segment cap, or nothing would free memory until the window ends. Reason: section 6.5's regions belong to the pool they were read into, wherever their stream lives (D24).
- **D74.** `SlabBytes` holds a `Bytes` and an `Arc` to its tracker, so one reference change is two atomic operations: per batch, but two. The tracker is what knows the slab's size and when it has gone. Regions come from one `BytesMut` split apart, so there is no `unsafe`, and the server crate forbids it. Slab memory is never recycled: a new slab is a new zeroed allocation. Reason: one count per slab with an in-place write would take `unsafe` for a saving nothing has measured.
- **D75.** *Superseded by M7 (D134 to D145) on a node started with `Node::recover`, which is what the binary does; `Node::start` still behaves as written here.* Replay-based recovery, WAL recycling and checkpoints wait for M7: nothing here calls `try_recycle`, so WAL files accumulate until then, because D16 needs a checkpoint first. Each node starts at generation and `last_valid_id` from config, and an uploaded object is only reported, not yet recorded as an extent.
- **D76.** An `incr` path is limited to 256 keys, the depth the CBOR parser accepts, and refused before anything is built. An `incr` that adds a key is parsed again before it is accepted, and anything the parser can't read is error 8 with nothing changed. An `incr` on an existing number can't change depth, and a merge can't go deeper than the deeper of two docs that both parsed, so neither pays for this. Reason: section 3's validation bounds a doc's size and form, but a flat `path` turns into nesting only when applied, so a long one overflowed the core's stack and aborted the node, and a shorter one committed state that no later merge, incr or replay could read. A re-parse is the one check that can't disagree with the parser. Parsing every result was measured first and added about 78% at 64 KB, which is why it is limited to the one case that can deepen a doc.
- **D77.** A stream moved while its stamped entry is queued on the old core (D7) keeps its id order in the WAL. The handoff lists `(core, ticket)` for each such entry, and what the new core stamps after adopting it stays in that core's own queue until the earlier core says, by message to all cores, that the WAL channel has taken up to that ticket. Channel FIFO then keeps the order. The move itself doesn't wait, and the new core may stamp and level 1 ack one write before its queue stops further reads. A core's tickets must reach the WAL in order, so anything it stamped after adopting the stream waits too, including other streams' writes. Only what was stamped before can be waited on, so a wait always points at an earlier stamp and two cores can't wait on each other. If the WAL has stopped, the wait is released, since nothing further reaches the file. Reason: replay applies entries in file order, and a later id fsynced first could leave a gap below an acked id; deferring the handoff instead would hold the control thread for as long as the WAL stalled.
- **D78.** Adopting a shard is not finished until what the new owner earlier forwarded for it has arrived. The adopter holds the shard's writes and sends a probe down the route it was forwarding on, through the forwarded inboxes, so per-link FIFO keeps the probe behind those writes at every hop. The owner it reaches answers, and only then do held writes run and the move's `done` fire. A core's own forwards coming back go first, ordered by when it first forwarded each, since reading a write just before an `Adopt` can send it round a second time. A stream the handoff first tells the core has its own shard gets a probe of its own, because its route changes too. Every core always reads its forwarded inbox: a stalled core passes on what isn't its own and keeps the rest in order, handing those on when it gives the stream away, so a probe never waits on the WAL. The control thread runs one move at a time, so at most one hold exists and only at the owner, which is why probes can't wait on each other. This replaces reading control before each write, which only narrowed the window. Reason: D65's barrier is answered by whichever core owns the stream, so a shard returning to the client's route core answered it immediately, and a publish still on the old path could be overtaken, then dropped as an older duplicate and acked as committed without being written.
- **D79.** Once the WAL writer has stopped, each core learns it from the durable watch closing or a failed `try_send`, and goes on reading writes in order to refuse them. A new publish gets `NACK` and a state op gets `ERROR`, both code 4, with a message naming the cause. A level 2 or 3 write already stamped gets `ERROR` rather than `NACK`, since it may be in the file and section 3 says a `NACK` committed nothing. Level 3 writes already handed to an upload stay waiting, since that upload can still succeed. The core keeps serving control and reads. Reason: refusing to ack was right, but a permanent failure looked to clients like endless backpressure. See Q22 for the code.
- **D80.** `Node::move_shard` returns false and `Node::set_override` returns `None`, with nothing changed, for a core that doesn't exist, a shard past the table, or an override shard with no stream yet. The control thread checks, so a core never sees a bad argument. Reason: these reached a core or the control thread as an index out of bounds and took it down, and the config and CLI layers will call them.
- **D81.** State is read and written by a small RFC 8949 reader and writer in `state.rs`, still using `ciborium`'s `Value` as the tree, because `ciborium`'s own decoder refuses simple values and turns undefined into null. Simple values, undefined among them, are held in `Value` as the never-valid tag 2^64-1 on their number, and a doc that really uses that tag is refused. Only null deletes in a merge. `incr` reads a bignum (tags 2 and 3) as a number and writes back a plain integer, with an overflow error if it doesn't fit one. Nesting stays limited at 256, where `ciborium` limited it. Results are still re-encoded in shortest form, except floats, which are 4 or 8 bytes and never 2. Reason: section 3 rejects a doc only if it isn't valid CBOR, and section 10's merge deletes only on null.

### Delivery

- **D82.** A connection lives on a home core (D24), and its subscriptions' queues live there. The owner holds each stream's filter table, with subscriber counts per home core, and checks each visible batch once per distinct filter. A home core lists subscribers per filter id and shares the owner's answer out, so the filter check doesn't depend on the number of subscribers or which cores they are on. Reason: sections 5.2 and 6.1 together. Filter ids aren't reused, so a late message can't be taken for a later filter.
- **D83.** A read step walks the cores that stamped the ids in question, oldest first, then ends at the owner, who compares the batches found with its extents and picks whichever holds the lowest id. A core lets go of an uploaded batch only after the owner has confirmed it has the extents (`AddExtents`, `ExtentsNoted`), so anything missing from the walk is in the owner's extents by the time it looks. Each hop only gives ids in its own stretch of `owners`, because a stream moved away and back has two stretches on one core with another's in between. Reason: D68 leaves batches on the core that stamped them, and a reader must not skip the ones uploaded while the extent message is on its way. Extents are kept in RAM until M7. This also supersedes the limit noted in D68.
- **D84.** A stamped batch is visible once all earlier batches are and, if it asked for level 2 or 3, its ticket is durable (BUILD_PLAN's rule). Batches not yet visible move with the stream, holding `(stamping core, ticket)`. A core giving away such a batch owes all cores a `DurableSeen` when its ticket is durable, and each keeps the highest it has heard, so it doesn't matter how far the stream has gone by then. After the WAL stops, a waiting batch never becomes visible, and neither does anything behind it, including level 1 records already acked (section 7.2 lists level 1 as lost on a process crash, and the node needs a restart at that point anyway: D79).
- **D85.** Messages from owner to home core carry a sequence number per `(stream, home core)` that moves with the stream, and the home core puts them back in order. Reason: after a move, the old and new owner send on one channel from two threads, and ids must still arrive in order. The channel is unbounded, since an owner never waits for a subscriber; a home core drops what is over its bounds. Fan-out has its own channel, read below writes, plus up to 16 messages per loop, so neither can starve the other. A home core keeps a stream's entry, which holds that number, for good. M7 should drop it with the stream.
- **D86.** On overflow a subscription's queue is dropped, so the bound holds right away, and `BEHIND.resume_from` is the last id it was given. The subscription leaves the filter table and catches up by itself from that id, starting only once the client is reading again. `BEHIND` isn't subject to the connection's window, and a stalled client gets only one. An empty queue accepts one batch of any size, so a batch over the bound can't loop for ever.
- **D87.** A catch-up read tries the local tier first, and any failure there falls to the object store, whose answer is what counts. Not found is error 7, and a CRC or format failure is error 8, both ending the subscription. Any other store error retries every 100 ms for as long as it lasts. Reason: a store outage shouldn't cost the client its subscription; a corrupt object won't improve.
- **D88.** `WITH_STATE` puts the state in `SUBSCRIBED`, and without it `state` is empty, with `state_ver` always present. `STATE_ONLY` wins over `WITH_STATE`: `SUBSCRIBED` has the state, no records follow, and each visible state change sends `STATE` with the doc as of that change. For a client not reading, only the latest is kept. Reason: Q23, and state is "how things stand now".
- **D89.** `StreamConfig.retention_ms` is section 7.4's class, 1 day by default. An explicit `from` or stored cursor is error 7 only if a known record above it is older than the start of retention. Known means the first extent's first id if it starts above the cursor, otherwise that extent's last id, the next id in memory on the owner or an earlier owner (D100), or the head. So an old cursor at the head isn't an error, a cursor inside retention never is, and a cursor inside an extent that crosses the start is served, because telling what follows it would take reading the object: records past the start can be delivered then, and nothing is missed. `from = 0` starts at `make_id(now - retention, 0)`. Reason: "a read before the start of retention" means something would be missed.
- **D90.** A stored cursor wins over `from`. A new name is stored as where the subscription starts. `from` above the head is accepted, and means nothing is delivered until ids pass it. `from = u64::MAX` starts after the stamped head, which is what `SUBSCRIBED.head` reports, so a record stamped but not yet visible at that moment is skipped. A `COMMIT` above the head, or on a subscription with no name, is error 8 and changes nothing; a reset to any id is allowed. Reason: section 5.1 is silent, and a commit above the head would skip records yet to be written.
- **D91.** Fair sharing is turns: each subscription with something due sends `fair_share_bytes` (256 KiB, or less if `max_frame` is smaller), and always at least one whole record, then goes to the back. A DATA frame is one turn. `connection_window_bytes` (4 MiB) is how much a connection can have untaken, which stands in for the socket until M6. Bytes are never split inside a record, so one record bigger than a frame's limit still goes alone. Reason: the smallest thing that bounds a heavy subscription's share.
- **D92.** Linger counts from the first record queued, on real time, and a `linger_ms` of 0 goes at the end of the event. A catch-up read doesn't linger, since it isn't waiting for more. `PROGRESS` also runs on real time, checked at a quarter of the interval, and goes only with the queue empty and the connection's window open. So it never overtakes a match. Reason: tokio timers can't follow `ManualClock`, and neither is part of a record's identity.
- **D93.** Read tasks are `tokio::spawn`ed on the home core, one at a time per subscription, so a slow store delays that subscription alone and the core goes on. A new read asks for at most `catch_up_read_bytes` (1 MiB), once the queue is at or under half its bound. Reason: section 6.1 says a core never blocks; the object store's API is async.
- **D94.** `Node::connection` is the in-process stand-in for a socket, on the model of `Client`. M6 wires frames to it. `SlabBytes` are held in shared `Matched` values, so memory delivery costs one `Arc` per subscriber per batch and no slab reference change per subscriber. A batch waiting for visibility holds one more slab reference, so a publish now makes 10 reference changes, up from 8.

### Delivery bounds

These follow the delivery decisions and change them where they say so. Tests: `crates/server/tests/delivery_bounds.rs`.

- **D95.** `STATE` frames take from the connection's window and return it when read, as `DATA` does. Reason: a client reading everything lost the window for good, and everything on that connection stopped.
- **D96.** A queue and a window count the memory they keep alive, not only matched bytes, because one tiny match holds a whole slab or read buffer. A queue costs the larger of its bytes and its allocations' sizes, where neighbours in one allocation count once. A frame moving to a new allocation costs that allocation's size, up to 1/8 of the window, and is returned when read. So unread frames hold at most the larger of the window or 8 allocations per connection. The queue bound and the window are both lowered to a quarter of `memory_cap_bytes` if they are above it, since past the cap publishers stop before any bound does. Reason: the only way to bound this without copying records (section 5.2) or a new message. The 1/8 keeps a window open across slab crossings, so a client that is reading and has a long round trip isn't falsely `BEHIND`. Limits: bounds are per subscription and per connection, so enough stalled clients, each holding different slabs, can still reach the cap together. Identity is compared only with the neighbouring item, so a queue alternating between slabs counts some twice, which errs towards `BEHIND`. Two subscriptions on one connection each pay for the same slab.
- **D97.** A subscription overflows only with its connection's window closed. With the window open the end of the event sends the queue, so a batch past the bound isn't a slow client, and the bound can be passed by what arrives in one event. Linger's "queue reaches the frame size" means the smaller of the frame's data limit and half the queue bound, or allocations reaching the whole bound. Reason: the defaults (8 MiB queue, 16 MiB frame) made the frame-size trigger unreachable, and section 5.2 says a queue reaching the size goes out. This is a working reading of section 5.2, which assumes a frame fits the queue. Changes D86 only in when overflow applies.
- **D98.** `SUBSCRIBED` and a snapshot show the state as of the last visible change, with `head` at the last visible id while anything stamped is waiting. `from = u64::MAX` therefore starts after that head. This replaces D90's "starts after the stamped head", so a record stamped but not yet visible when a subscriber arrives is now delivered, not skipped. Reason: a version a crash can take back must not be readable, and state plus the log from `head` has to add up (section 10). `expect_ver` still checks the stamped version, because later ops have to chain. During a shard move a client can have its ack before the new owner hears of the durability, and a snapshot in that gap shows the previous version with its matching head: stale, not wrong. A frame's budget: D91's "at least one whole record" now applies only to an empty frame, so a large record after a small one starts a new frame.
- **D99.** Publishers can stop only while slabs are pinned, and overflow only happens when a record arrives, so stalled subscribers could hold the cap for good. Each home core checks every 50 ms whether any core's slabs have reached 3/4 of `memory_cap_bytes`, and if so takes everything back from a connection whose frames waited through a whole check with none taken: its queues and its unread `DATA`, with the `PROGRESS` behind that `DATA`, since it would claim past what is gone. Frames are in an `Outbox` the core can reach, replacing the channel (Q27). Each affected subscription gets `BEHIND` from the last id the client can have seen, exactly, as removal is atomic with the client taking a frame. It starts catching up only once the client has read a `BEHIND`, which it reports, so a stalled client holds nothing and costs no reads. Publishers can still wait up to about two checks at the cap. A client reading at least one frame per check isn't stalled, so slow readers can still slow publishers while they read. Frames of store reads, which aren't slab memory, are only taken back along with these, so a node with many stalled connections can hold one window or 8 read buffers each until something else causes pressure. Reason: section 5.2's bound, per queue, says nothing of their total, and M5 asks that a slow subscriber leave the publisher alone.
- **D100.** The retention check of an explicit id below the start asks the stream's earlier owners what they hold above it, in `ControlMsg` hops, oldest first, before anything is answered, since their unsealed batches aren't on the owner (D68). A move during the walk restarts it at the new owner. A subscriber at or inside the start asks nobody. Ids within a batch have no gaps, so memory answers exactly. Reason: otherwise the same read is error 7 or not depending on whether the stream moved.
- **D101.** Catch-up's read steps, read chains and finished store reads have their own channel, polled below writes and fan-out. A core does one per turn when anything else was waiting and 5 when nothing was. Before this they ran on the biased control inbox and each step queued the next, so a core with catch-ups going read no writes until the last finished. One read per busy turn means catch-up can't starve either way. A read's cost is bounded by `catch_up_read_bytes`, so that is what a write can wait for per turn. A reply a home core gets from another core's owner is still in its delivery channel, so up to 17 of those per turn: not measured separately. D83's order holds: it relies on extents being noted before a batch is dropped, not on channel order.
- **D102.** `PROGRESS` takes 13 bytes, its frame's size, from the connection's window, returned when read. So unread ones are bounded in bytes like `DATA` and `STATE`, and a position still to report waits for the window, as D92 already had it. Reason: a client not reading, with a rare filter, otherwise queued one frame per interval for ever and never got `BEHIND`. `SUBSCRIBED`, `BEHIND` and errors aren't charged: `BEHIND` is at most one per stall (D86), and the others answer a command. A client sending commands and never reading can still grow its frames with errors: not fixed, as M6 stops reading commands from a socket it can't write to, or should.
- **D103.** `filter_check_count` is incremented where `Filter::matches` runs, in `Matched::select`, on the owner. Catch-up's checks on a home core aren't in it, since section 5.2's count is about live delivery.

### Recovery

- **D14.** Ownership is stored as `ownership/<generation>` created with `PutMode::Create`; the highest generation is current. Each holds the previous generation's last valid id. Reason: the same conditional write works on S3 and `LocalFileSystem`, and a losing process sees a clean failure.
- **D15.** Id assignment is `max(last_id + 1, now_ms << 16, last_valid_id + 1)`. Reason: new ids stay above everything a former owner could have issued.
- **D16.** The WAL is recycled only after both the segment and its checkpoint are durable, and replay skips ids at or below the stream's sealed extent. An uploaded object with no extent is ignored and ages out. Reason: a crash between steps neither loses nor doubles records.
- **D17.** Compaction applies the last valid id too, and drops an older generation's records above it. Reason: compaction must not resurrect what readers would ignore.
- **D18.** Checkpoint files are `checkpoints/<generation>-<seq>.ckpt`, in the same paged footer format. A lookup walks newest to oldest using cached top indexes, and a periodic full checkpoint removes the need for older files, which the next startup deletes (D147). Reason: the simplest way to bound the walk (Q8).
- **D19.** Fjall with default features off. Reason: pure Rust, and its default `lz4` feature would break the no-codec rule.
- **D20.** Deleting a stream writes a tombstone to the local store and checkpoint, and its old records stop being reachable and age out with their prefixes. Reason: rebuild must not resurrect it, and "nothing else deletes data".

### API, auth and sinks

- **D21.** Admin routes, all under `admin` (Q2): `PUT` and `DELETE /v1/stream/<id>` (create or config, delete); `PUT`, `DELETE /v1/stream/<id>/sink/<sink_id>`; `POST .../sink/<sink_id>/pause`, `/resume`, and `/reset`. Bodies are JSON. Reason: the smallest set that reaches what the spec already requires.
- **D22.** WebSocket and HTTP share one TLS 1.3 port, with the upgrade at `/v1/ws`. Reason: one listener.
- **D23.** The server has its own small RFC 6455 frame reader, tested against `tokio-tungstenite`. Reason: existing libraries read into their own buffers, and section 6.5 needs frames read into slabs and unmasked in place.
- **D24.** Connections are accepted once and handed to cores round robin. Bytes read on a non-owner core reach the owner as an exclusive slab region in a message, and are stamped there. Reason: a connection can use streams on several cores, and `SO_REUSEPORT` balancing isn't portable to macOS.
- **D25.** Tokens are `body | hmac_sha256(secret, body)`, with a little-endian binary body: `expiry_ms u64 | author u64 | n u16 | n × (pattern str | perms u8)`. Patterns match exactly or by a trailing `*`. A token with `author = 0` is invalid. Expiry is rechecked on every operation. Reason: verification needs no lookup, and HMAC is also what webhooks need.
- **D26.** HTTP: binary publish uses `Content-Type: application/x-sillystream-records`; any other type is the simple form. `filter=` is comma-separated `eq:<mask>:<value>`, `any:<mask>`, `author:<n>`. `PATCH state` takes the op in `X-State-Op`. Results for publish and state are small JSON objects; reads are binary. Reason: the spec names these but gives no encoding.
- **D27.** `sink_id` is a `u64`, and clients may not create cursors named `sink:*` (error 8). Reason: `forward` uses it as `producer_id`.
- **D28.** Sinks never forward or deliver system records. Reason: forwarding `author = 0` would inject state ops into the target.
- **D29.** `webhook.deliver` posts the record bytes unchanged, with `X-Sink-Id`, `X-First-Id`, `X-Last-Id` and `X-Signature` (HMAC-SHA256 over the body). The resolved address is what gets checked against private ranges. Reason: fixes the spec's fields to a form, and blocks DNS tricks.
- **D30.** A sink's skip gap is logged and shown in the stream info. Reason: the spec says "records the gap" without a place.
- **D31.** A stream's retention is read at compaction time; changing class affects data from that point on. Reason: compaction copies forward and nothing rewrites old prefixes.
- **D32.** Test hooks are behind a `test-hooks` cargo feature of the server binary: a clock offset and named crash points. Reason: retention and crash windows can't otherwise be reached end to end, and release builds must not contain them.
- **D104.** Each core's sockets read through a thread-local slab pool with non-suspending `try_read` under `Waker::noop()`, and borrow part of a slab only for the read. Reason: section 6.5 and invariant "cores share no locks"; an idle connection then holds nothing.
- **D105.** TLS and the HTTP upgrade run on the connection's home core, chosen round robin at accept (D24). Reason: simplest placement; a handshake storm slows that core's streams and is unmeasured here.
- **D106.** Reads try rustls before waiting on the socket, and again after any read that didn't come back empty. Reason: rustls can hold plaintext that came with bytes it already took (a client's first request with its Finished), and the socket says nothing more about it. Tests hung without this.
- **D107.** rustls copies on both paths, so section 6.5's in-place unmasking happens in the slab after rustls has decrypted into it, and nothing is zero-copy through TLS. Reason: rustls's API; kernel TLS isn't in scope.
- **D108.** A second `HELLO` renews the token on a connection and answers `WELCOME`. When a token expires, the connection's subscriptions end with error 1 and later ops fail with error 1. Reason: section 12 says expiry applies and gives no other renewal; a connection needn't drop to renew.
- **D109.** Before `HELLO` a frame may be at most 128 KiB, `HELLO` must come within 10 s, and an over-limit header there gets `ERROR` 6 and a close. After `HELLO`, an over-max frame gets `ERROR` ref 0 code 6, its payload is discarded and the connection continues. Reason: an unknown client mustn't make the server read a large frame, and a known one has only sent one bad frame.
- **D110.** Fragmented messages are copied together, the slow path. Reason: section 11 sends one frame per message, and fragments come only from other clients and proxies.
- **D111.** HTTP: `Content-Length` bodies only (chunked is 400); ids in JSON are decimal strings; status 1→401 or 403 when the token is good but doesn't grant it, 2→404, 3→409, 4 and 5→429, 6→413, 7→410, 8→400, and 405 for a wrong method; `ack=0` answers 202; `PATCH` state defaults to merge, with `X-State-Op: set|merge|incr|1|2|3`; `If-Match` takes a number, a quoted number or `*`; `PUT` cursor takes a decimal or `{"id":...}`, with `?reset=true` to go back; the read route answers with `x-head`, `x-through` and `x-count`; `X-Codec` sets a simple publish's codec. Reason: section 11.2 and D21 and D26 leave these open, and these are the plainest HTTP meanings.
- **D112.** The server has its own small JSON reader and writer (`net/json.rs`). Reason: server crates may not depend on `serde_json`, and only config and replies use it.
- **D113.** Sinks at M6 are a registry: routes store, pause, resume and reset them with a `sink:<id>` cursor, and nothing runs until M9. Reason: section 11.2's routes are M6 scope and the runtime is M9's.
- **D114.** A deleted stream leaves a tombstone holding its last id, and a stream created under the name later starts above it. Reason: invariant that ids are never reused, with a clock that may not have moved.
- **D115.** *Removed with M7, as it said: the binary now replays.* The binary refuses to start over a `wal_dir` holding WAL files. Reason: replay comes with M7, and starting would ignore what they hold. Remove this with M7.
- **D116.** SDK: the socket and all unanswered work belong to one task, and a separate writer task means a socket with no room never stops reads. Publishes wait in a per-producer FIFO until acked and are resent in order with the same seq after a reconnect; state ops fail with `Disconnected`, since they have no dedupe key; a level-0 publish is forgotten when written. Reason: section 3's retries, with no guess on a state change.
- **D117.** SDK: a record with `count > 1` holds `count` little-endian `u32` end offsets then the item bytes, and zstd covers the whole of that, with `codec = 1` only when it came out smaller. Reason: section 2 leaves the layout to the client. Dictionaries (section 3's "if used") aren't built.
- **D118.** SDK: a subscription whose unread queue passes its byte limit is unsubscribed, and comes back from its cursor when half has been read. Each resubscribe takes a fresh sub id, so late frames are recognised. Reason: no queue may grow without limit, and the driver must keep reading for other subscriptions.
- **D119.** SDK trusts only the CA PEM it is given, with no system roots. Reason: no extra dependency; pass a bundle for a public CA.
- **D120.** `sillystream bench` starts the real server binary with its own temporary directories and certificates, takes level 0 as publish to delivery, and level 3 at a fixed rate of 50 per second. Reason: the milestone asks for levels 0 to 3, and level 0 has no ack while one-at-a-time level 3 would give a sample a second.
- **D121.** A WebSocket frame that spans reads collects in its own heap buffer, grown by doubling from what has really arrived, and is copied into a slab once whole. Reason: a header only claims a length, and allocating that claim from the slab counted it against the memory cap, so 260 connections sending about 15 bytes each stalled every publisher on a core. Cost: one more copy for frames spanning reads, against section 6.5's "allocated once" reading of the slab path; the slab allocation itself still happens once. The M6 throughput table re-run shows no drop (`docs/BENCH.md`). A frame or fragmented message must finish within `partial_frame_timeout_ms`, 60 s by default, or the connection closes, because what did arrive is real memory. That sets a floor of about 2.2 Mbit/s for a 16 MiB frame.
- **D122.** `wsconn` keeps the retry time for a write waiting on a full node across wakes, and polls timers ahead of the socket and node in its biased `select!`. Reason: a fresh 1 ms sleep behind `recv_reply` and `recv_event` never fired while frames kept arriving, and the connection stops reading while a write waits.
- **D123.** Events wait while either reply or data bytes are over their mark. Reason: `STATE` goes out as a reply, which the event gate ignored, and taking an event returns its window credit. Left in the connection, the window closes and D88 keeps only the latest state.
- **D124.** The SDK checks a frame against the current `max_frame` when it leaves, in `send_ready` and for a state op, and answers `TooLarge`. Reason: the server's error 6 has `reference = 0`, so it can't name the frame. An error with reference 0 other than 1 is still ignored by the SDK, because it can't say which call it answers. The SDK's own frames no longer reach that case by size, and no way to reach it by decode failure is known.
- **D125.** A renewal `HELLO` ends with error 1, after `WELCOME`, every subscription the new token doesn't grant read on. `COMMIT` on one of those, or on anything once the token has expired, is error 1. Up to `max_subscriptions` ended ids are remembered per connection for that answer; past that a `COMMIT` on one gets error 8. Reason: section 12 revokes by expiry, and a renewal could otherwise take nothing away.
- **D126.** HTTP publish takes at most `max_frame - 10` record bytes, refused with error 6. Reason: delivery adds `DATA`'s 10-byte prefix, D43 says `max_frame` covers the whole frame, and one record can't be split. **Not fixed:** the system record of a large state doc can still exceed this when `max_frame` is set close to 64 KB, by code reading only; the 16 MiB default can't reach it.
- **D127.** `Subscription::next` opens a frame record by record. A record it can't open costs only itself, and comes as `SdkError::BadRecord { first_id, last_id, too_large }` after the items before it, without ending the subscription. `max_decompressed_bytes` now bounds what one `next` holds, so a large frame comes as several `Items`; a single record over it is `too_large`. Peak use is about twice the limit, since the record being opened is held beside the items. `decode_records` stays all or nothing, and its limit now covers the whole run. Reason: data is opaque (section 2), so any publisher can write such a record, and a per-record limit let small bombs multiply. A consumer that commits past a `BadRecord` gives up those ids, which is now visible to it.
- **D128.** A connection attempt has one time limit from socket to `WELCOME`, the larger of `ping_interval_ms` and 10 s, and runs beside the command channel, so `state_op` answers `Disconnected` and publishes queue while it waits. An attempt that succeeds after `set_token` changed the token is dropped and retried. Reason: a peer can accept and then say nothing at any step, and no socket error reports that.
- **D129.** `wsconn` refuses a `SUBSCRIBE` on an id it already has, or naming a `sink:` cursor, itself, with the same error 8 the core gives. Its `subs` map stays written before the core answers, so that a renewal also ends a subscription still being attached, and the refusals it can't predict (errors 2, 5 and 7) already remove their entry. Reason: an error 8 can't be read as a refused subscribe, since a bad `COMMIT` gets one with the same reference, and an overwritten entry made a renewal check the wrong stream.
- **D130.** An HTTP publish's body collects in its own heap buffer, as D121 does for WebSocket frames, and moves to a slab once whole. Reason: 260 connections sending only a head claimed 4 GiB of slab for 30 s each and stopped every publisher on the core. Cost: one more copy on every HTTP publish, since unlike a WebSocket read nothing here borrows the slab first. HTTP's body wait stays `REQUEST_TIMEOUT_MS` for the whole body. What really arrives is bounded by that wait and `max_frame` per connection, and connections aren't limited (see the unfixed finding on HTTP responses).
- **D131.** `SUBSCRIBE`, `UNSUBSCRIBE` and `COMMIT` from a socket each carry a ticket, a counted drop guard that travels with the command across cores, including a `COMMIT`'s second trip to the owner and a subscribe's attach, and ends wherever the command does. `wsconn` looks at no more frames while 256 are out on its connection, and tries again every 1 ms with what the existing backlog holds. Reason: these commands use the core's unbounded control inbox and a `COMMIT` has no reply, so nothing slowed a client: 20-byte frames grew the server by about 225 bytes each, and other requests on the core waited behind them. The count is one atomic per connection, not a lock. The limit is at least 256 commands per ms per connection, far above any cursor's real rate. Only the `COMMIT` flood has a test (`crates/server/tests/command_flood.rs`, 1 core): the other two share the gate, and a multi-core owner wasn't run. A `Detach` a home core sends after an unsubscribe has no ticket; it follows an attach that had one.
- **D132.** `DATA` frames a connection has taken for its socket keep their slabs for at most 50 ms. After that `wsconn` copies what they have left to write into its own heap, and they go on to the socket in order. Reason: D99's take-back only reaches the `Outbox`, and the 256 KiB gate counts record bytes, so one token with only read could hold thousands of slabs with tiny matches, for as long as it kept the socket open, and stop every publisher homed on that core. With the copy, the gate's bytes are the real cost, frames beyond it stay in the `Outbox`, and D99 can take them back. It runs whether or not memory is short, which keeps it one rule. Cost: a client whose socket stays full gets a copy of at most what the gate lets wait, every 50 ms, against section 5.2's "no copy"; rustls copies every record anyway. A stalled connection holds at most 256 KiB, or one frame if that is more (up to `max_frame`), of heap for as long as its socket stays open, since a WebSocket has no write timeout and connections aren't limited. The test uses a 64 KiB slab and an 8 MiB cap on one core, and defaults or several stalled connections weren't run.
- **D133.** HTTP at level 0 runs the owner's own header checks before it answers 202, and a refusal is the same 400 and error 8 other levels get. Reason: section 3 says a rejected publish gets a `NACK`, and a caller was told a malformed body was accepted. The checks are one function the owner calls too, and read no data. They run twice for this path only. What depends on the stream isn't checked, which at level 0 over HTTP is nothing that can refuse: a duplicate isn't a refusal, and HTTP publishes carry no state change. The separate `min_ack` finding stays open. WebSocket isn't affected, as its client hears the `NACK`.
- **D134.** Metadata is kept only by a node started with `Node::recover`/`Server::start_recovering`. `Node::start` keeps no store, as before. Startup order: read ownership, read the WAL, read the checkpoints, open the local store, scan objects, put each stream's replay together, claim the generation, and only then start threads and hand streams to the cores (before anything else reaches their control channels). A loser of the claim has written nothing. Reason: section 8.1's "one path", with the only shared write last.
- **D135.** Ownership is `ownership/<gen:020>`, 32 bytes: magic, generation, last valid id, CRC32C, zero. Local store keys are `'s'|len u16 BE|name` for a stream's fields and `'x'|len|name|id_first BE` per extent, plus `'g'` (largest id) and `'c'` (this store has seen every stream). Stream ids over 65,000 bytes are cut there with an XXH3-128 of the whole, since a key is at most 65,535 bytes and an id can be that long (D57); the value holds the whole name and a read checks it, so a collision is an error and never another stream's data. Reason: keys are ordered and bounded, and a seal writes one key per new extent, not a stream's whole list.
- **D136.** What a checkpoint saves is the stream as of its last visible record: `visible_through`, `visible_state` and a shadow dedupe table updated in `drain_visible`. Reason: a stamped publish a crash can erase would otherwise be acked on its retry from a saved dedupe entry, unwritten. Cost: one more small table per stream that has a producer. `last_id` is the true last stamped id, so ids stay above it either way. Known limit: a level 0 or 1 state change that became visible can be in a snapshot while a crash erased its records from the WAL, so state can refer to an id that no longer exists. Q7's level 0/1 wording accepts losing such a change, not this shape of it, so see Q7. A level 1 publish lost in a crash can also be retried at a higher level with its dedupe entry gone, and is simply written.
- **D137.** A seal's checkpoint runs after its upload, in control, in two rounds to every core: is everything sent to the WAL before this seal's rotation uploaded, at its owner, and visible (and no batch behind it), then what changed. A WAL file is recycled, and objects are listed in a checkpoint, only after a clean first round; otherwise both wait for a later seal. Reason: this fixes the earlier finding that a seal could leave acked records of a closed file behind, and listing an object whose extents hadn't reached a gather would hide them from the startup scan. Cost: a seal with a stream mid-move or a busy unsealed batch recycles nothing that round.
- **D138.** A record of a former generation with `last_id` above the limit is ignored whole, even if its `id` is below (`count > 1`). An extent crossing the limit is kept with `id_last` lowered to its last whole accepted record, found by reading headers (no data), and reads stop there. Reason: section 8.1 says ids above are ignored, and half a record has no meaning.
- **D139.** A checkpoint file's head is stored under the empty stream name, with `full`, `max_id` and the objects it covers. On startup, objects in no trusted file's list are scanned, and their extents adopted (D149). This refines D16: an upload whose checkpoint didn't happen, with the WAL also lost, still keeps its level 3 acks. Delta files hold only new extents, the walk unions them, and a full file (every 64 files, `full_checkpoint_every_count`) means older ones aren't read. A full file is built in memory by reading every file back, which is proportional to all streams; a large node will want this streamed, and it isn't.
- **D140.** A stream out of RAM loads off the core on one `meta-loader` thread: messages for it wait in order, and a load that has failed retries with backoff, since reporting an error as "no such stream" would make a new stream over an old name. Writes parked count against `write_inbox_capacity`, past which the direct inbox isn't read (D7). A shard leaving forwards what's parked, in order, and drops a late answer by ticket. Reason: it keeps the store off the write path. Cost: a store outage stops every load on the node, as there is one thread, and after a lost local store every name not seen before costs a walk of the checkpoints until `'c'` could be set. `'c'` isn't set again after that loss, which is safe and only slower. A plain miss on a complete store costs one local read, once per new stream.
- **D141.** Eviction runs after each checkpoint, per core, with `active_stream_limit` split over cores (at least 1 each). A stream can go if nobody is subscribed from any core, nothing is pending or in memory, and the checkpoint has all its changes; oldest `last_used` first, on the core's own count. Tombstones stay in RAM. A home core is told `Evicted` and its per-stream sequence restarts with the stream's. Eviction is only reached at seals, so a node with a seal window of 10 s lets go at that rate.
- **D142.** A delete on a node with a store forces a seal and answers after a later checkpoint has its tombstone (D20). If the WAL has stopped so no checkpoint can come, it still answers true, as the delete did happen in RAM, and a crash then can bring the stream back. A tombstone's `last_id` is the floor of a stream re-created under that name, kept in its metadata.
- **D143.** Config, sink and cursor changes are durable only at the next seal: after a crash a `COMMIT` can go back to what the last seal saved, which is at-least-once, and a config change can be lost. The spec has no WAL entry for them. Reason: the spec has nothing else that carries them, and adding a WAL entry is a new mechanism to raise with you first.
- **D144.** Crash points (`storage::crash_point`, env `SILLYSTREAM_CRASH_AT=point[:nth]`, feature `test-hooks`) call `abort`. The feature is on only through the server crate's self dev-dependency, so `cargo test` builds the binary with it and `cargo build` does not. `crates/cli/tests/cli.rs` runs its own `cargo build` of the same binary into the same path, so it asks for the feature too, or the matrix would run a binary with no crash points when both run. The crash matrix checks for SIGABRT, so it can't pass on another way of dying. A clean stop seals with a 10 s bound first, and a restart makes up whatever that left.
- **D145.** The empty-WAL warning needs a generation to exist and no WAL file. A crash between the ownership write and creating the first WAL file on a new node warns on the next start, wrongly but harmlessly, as nothing could have been lost. There was no way to tell these apart without another write.
- **D147.** Only a startup deletes checkpoint files, after claiming ownership, and only those older than the newest full file it trusts (one with `max_id` at or below its generation's limit). A running node never does, because it can't know it still owns the bucket: its full file may be over the limit a replacement has just set, and then the replacement needs the older files. Checking the ownership record first would still leave a race between the replacement's listing and its claim. Reason: this is the simplest rule that can be shown safe. Cost: files pile up until the next restart, about 8,640 a day at a 10 s window, and that startup lists them all. Its deletes run beside loads, so they delay none (Q8).
- **D148.** A seal's local write also holds the delta checkpoint file it owes S3, under the local key `'p'` as `generation u64 | seq u64 | file`, overwritten by the next seal that changed anything. A startup first creates that file at its original path, which is a no-op if it got there, then clears the key. Reason: a crash between the local write and the PUT otherwise leaves extents, a tombstone and other fields only locally, and nothing would ever send them on; finishing the interrupted PUT adds no meaning to the format. If that seal's PUT was to be a full file, the delta takes its path, and is enough, as the earlier files are still there. Cost: each seal's changed metadata is written locally about twice. Jobs run one at a time and a PUT is retried until it succeeds, so one file is the most ever owed. Crash point: `checkpoint.before_put`.
- **D149.** The time cut-off on the object scan is gone, and with it a checkpoint file's time. Instead a full file's list holds every object recorded so far, and a file over its generation's limit has its list ignored. Objects a startup looks at are recorded by the next clean checkpoint, so each is looked at once. Reason: object times said nothing about what was recorded, since the uploader and checkpointer run independently and a former owner's object can arrive at any time. Cost: a full file's head grows by one path per seal, about 700 KB a day at a 10 s window, and is rewritten every 64 files and held in memory. Nothing removes entries yet, because nothing expires objects yet; the delete job of section 7.4 will have to drop what it deletes. This also replaces the case D139 used to accept, an unclean seal's object passed over once its WAL was lost.
- **D150.** A tombstone's floor is the stream's last id or the generation's last valid id, whichever is higher. Reason: a former generation's late object can hold ids up to that limit which this stream never had, and they are all older than the delete. `is_valid_stream_id` now also refuses an id over 65,535 bytes, on every HTTP route and sink target, since a checkpoint page holds a name's length in a u16. `build_checkpoint` refuses one too.
- **D146.** One narrow case isn't handled: if the WAL is lost, a state op whose system record was only in that WAL is gone, even when records above it reached an object, so the stream's state misses that change with no sign of it beyond the empty-WAL warning. Reason: it is the unsealed loss that warning already reports.
- **D151.** The local store holds the generation it belongs to, under key `'o'`, written once this process has claimed. A startup that finds any other generation than the latest ownership record empties the store first and treats it as incomplete, so misses ask the checkpoints. Reason: section 7.6 has S3 back the local copy, and nothing else could tell that another generation had run on the bucket since. The file the store owes S3 is put there before this (D148), so an emptied store loses nothing. Cost: a crash between the claim and that write means one rebuild from checkpoints on the next start.
- **D152.** A WAL file's header is now 32 bytes: `magic u64 | seq u64 | generation u64 | crc32c u32 | 0 u32`, with `generation` the owner that opened it or reused it, and 0 for a node with no ownership record (`Node::start`). This extends D8. Replay accepts a file's entries up to `limit_for(generation)`, as it does objects, and an entry with any record over the limit is ignored whole, since a publish commits as one unit (section 3). Generation 0 has no limit. Reason: section 8.1 says an older generation's data is accepted only up to the last valid id, and the spec's entry layout has no room for a generation. A file holds one owner's entries, so its header needs only one.
- **M7: what wasn't exercised.** Real S3, EBS, power loss and machine loss: `InMemory` and `LocalFileSystem` only, and `abort` proves a process crash only, since what the kernel holds survives it. D32's clock offset at startup is left to M8. Two binaries with separate disks and one store aren't raced at the claim on real processes: that case is run in-process, held at the PUT, and at the claim function; real processes are run on one set of disks. A hung (not failing) store blocks `Node::shutdown` at the metadata threads. Parked-message forwarding during a move has no scripted race, only a load after a move. `crates/server/tests/move_stress.rs` still isn't mine and stays uncommitted.

## Review findings not fixed

From the review of `aceb637`. Each is confirmed by the reproduction given, and each is **not fixed** unless it says otherwise. None has a regression test yet.

- **High: the memory cap counts partly filled client slabs for good, so publishers wait forever with nothing outstanding** (`crates/server/src/node.rs`, `Client::publish`). Each client keeps its current slab until it is full, and only `retire_slab`, which nothing in the node calls, lets it go. Once clients × `slab_bytes` reaches `memory_cap_bytes`, pinned bytes can't fall: acks and uploads don't help, the wait has no exit even on a stopped node, and `try_publish` says `Full` forever. Defaults reach it at 1,024 connections per home core that each published once. It also goes against section 6.5's rule that idle connections hold no buffer. Reproduction: 1 core, `slab_bytes` 64 KiB, cap 128 KiB, two clients on core 0. Each publishes one small record at level 2 and gets its ack, then `node.seal()` returns `Uploaded`. `pinned_bytes()` stays 131,072, and the next publish is still pending after 3 s.
- **High: an incr path deeper than the parser's limit commits state that can't be read again.** **Fixed by D76**, listed here because it was reported with the unfixed set. `a_path_too_deep_to_read_back_leaves_state_usable` and `every_accepted_depth_stays_readable` in `crates/server/tests/state_depth.rs` cover it.
- **High: override and shard moves can create a forwarding cycle.** **Fixed by D66's new rule**, listed for the same reason. `crates/server/tests/override_moves.rs` runs both reported cases and a sweep of move orders. The sweep's clients start from a limited set of first hops, so it isn't an exhaustive proof, and D66 holds the argument.
- **High: a move with a stamped entry still queued lets later ids reach the WAL first.** **Fixed by D77**, listed for the same reason. `a_move_with_a_parked_entry_keeps_the_wal_in_id_order_and_replay_equal_to_live` in `crates/server/tests/moves.rs` covers it. On the old code that test failed in 1 of 2 runs, because it needs the race, and `parked_streams_swapping_cores_all_get_through` failed in both.
- **Medium: graceful shutdown drops level 1 acked records parked in outbound** (`crates/server/src/core.rs`). `ControlMsg::Stop` ends the core loop after one non-retrying flush, and the core drops `outbound`. Section 7.2 lists level 1 as lost on a crash, and a clean `Node::shutdown` that reports `wal: Ok` isn't one, and `NodeExit` doesn't count the loss. D77 adds one more way for an entry to be parked at that moment. Reproduction: `wal_channel_capacity` 1, `wal.hold()`, 3 level 1 publishes to one stream 5 ms apart, all acked. `harness.finish()` gives `exit.wal` Ok, and `wal.entries().len()` is 2.
- **Medium: a seal can leave acked records of a closed WAL file out of its segment, against D56's rule for recycling** (`crates/server/src/core.rs`, `StreamLog::take_unsealed`). D56 says everything in a closed file is in some core's section, but D68 takes one stay per stream, so after a move away and back the later stay is in the closed file and not in the seal. Nothing calls `try_recycle` yet. Once it is wired up as D56 describes, a crash before the next seal would lose level 2 acked records, so D56 and D68 can't both stand. Reproduction: 2 cores. Seq 1 at level 2, acked. Move away and back. Seq 2 at level 2, acked. `node.seal()` returns `Uploaded`, and `read_stream` holds only the first id, though both entries went to WAL file 1, which that seal's rotation closed.
- **Medium: `Client::recv` never returns `None` after the node stops** (`crates/server/src/node.rs`). The client keeps its own `reply_tx`, so `reply_rx` can't close, and a task waiting for a level 2 or 3 ack hangs with no way to learn it won't arrive. Reproduction: `wal.hold()`, publish at level 2, `harness.finish()`, and `timeout(3 s, client.recv())` times out. A write waiting for a barrier (D65) doesn't have this problem, since it also watches the core's inbox.
- **Medium: state ops and a core's atomic-publish copies bypass the memory cap** (`crates/server/src/node.rs`). `Client::state_op` has no cap check, and `bytes_with_system_record` allocates from the core's own pool without limit. When seals can't complete (Q9), a state-only client pins memory and never slows down, and it also stalls plain publishers sharing that home core's account. Reproduction: `manual_config(1)`, cap 1 MiB, slabs 64 KiB, `store.hold()`, 2,000 `Set` ops of a 60,000-byte doc, each awaited. All succeeded in 0.09 s, with `pinned_bytes()` at 131,072,000, 125 times the cap. No seal was requested in that run, and seals held at the store weren't run separately.
- **Medium: merge cost is quadratic in the document** (`crates/server/src/state.rs`, `merge`). `position` and `retain` scan the whole target map for every patch key, on the core's event loop. Merging a flat doc of 16,000 three-byte integer keys (64,003 bytes) into itself took 581 ms in a release build, about 2,000 times the 267 µs `docs/BENCH.md` reports, whose benchmark uses a small patch. Nothing else on that core runs meanwhile, and a client can repeat the op.
- **Low: each empty seal leaks an `in_flight` entry on every core** (`crates/server/src/core.rs`). `on_seal` always inserts `in_flight[Seal(n)]`, and `on_upload_event` returns early on `UploadEvent::Empty`. An idle node with the default window leaks 8,640 entries a day per core. Reproduction: with a temporary stat for `in_flight.len()`, 50 `node.seal()` calls on an idle 1-core node, each `Empty`, leave 50.
- **Low: an idle node rotates to a new WAL file on every seal, and nothing recycles them** (`crates/server/src/node.rs`, `begin_seal`). With `DirVolume` each rotation creates a preallocated file, so `wal_dir` grows with no traffic, 8,640 files a day by default, and a later create failure ends the writer (`WalError::Rotate`) and stops writes on the node.
