# Build notes

Choices made where `docs/SPEC.md` is silent or ambiguous, and questions for the user. SPEC.md stays the source of truth: nothing here changes its meaning, and any item can be reversed. Each entry is one choice and its reason. Later milestones append here.

## Questions for the user

Each has a working assumption so the build can continue.

- **Q1. No `to` on subscribe.** Section 4 says an id range "from any point to any point", but `SUBSCRIBE` and HTTP `read` carry only a start (`from`, plus `limit`). Assumption: no new field; the client stops at its end id.
- **Q2. No admin API.** Sections 9, 12 and 13 require stream create, config, delete and the sink lifecycle under `admin`, but section 11 has no route for them. Assumption: the smallest HTTP additions, listed in D21.
- **Q3. Manifest record type.** Section 7.5 publishes seal manifests to a system stream, and only `author = 0` data may be read by the server, but section 2.2 defines entry types 1–3 only. Assumption: manifests are system records with entry type 4 in a stream named `_sys.manifests`.
- **Q4. Manifest stream's special rule.** Section 7.5 says one is needed but not what it is. Assumption: manifest stream segments are never listed in a manifest and never compacted; they stay in `sealed/`, and the delete job's compaction check covers them.
- **Q5. "One preallocated file" versus recycling.** Section 6.3 has one file, but entries covering a sealed-but-not-yet-uploaded window must survive while new ones arrive, and old entries in a recycled file still have valid CRCs. Assumption: D8.
- **Q6. One "last valid id" with per-stream ids.** Section 8.1 keeps a single id, but ids are per stream. It works because ids are time-based: it is the highest id seen at takeover, and every new id on every stream is above it (D15). An old generation's object at or below that id is accepted. Please confirm.
- **Q7. Lost records at levels 0–1 and id reuse.** A record delivered at level 0–1 and lost in a crash leaves no trace, so "ids are never reused" cannot be proven for it. A restart normally moves past it because ids follow the clock; a backward clock or borrowed ms could collide. Assumption: the no-reuse guarantee is tested for WAL-durable records only.
- **Q8. Checkpoint lookup and cleanup.** Section 7.6 puts checkpoints in shared files per seal, but does not say how a long-idle stream finds its latest one, or whether old files may be deleted ("nothing else deletes data" is about records). Assumption: D18.
- **Q9. Upload outage.** The spec doesn't bound memory and WAL while S3 is down. Assumption: slabs and the WAL stay pinned, and when a configured cap is reached it becomes publisher backpressure (D7). Level 3 acks wait.
- **Q11. `eq` value bits outside the mask.** Section 4 defines `eq` as `(options & mask) == value`, which is never true if `value` has bits outside `mask`, but the formula in section 4.1 uses `need1 = mask & value` and would report "all match" for such a clause. Assumption: section 4's definition wins (D33).
- **Q12. `ACK.count` is a u32.** A maximum-size frame can hold about 500,000 empty records of 65,535 items, around 3.4 × 10^10 items, which `ACK.count` can't express. Section 3's rejection list doesn't cover it. Assumption: D34.
- **Q13. Nothing bounds how far ids can run ahead of the clock.** Section 2 says the id is the item's timestamp and that the owner borrows the next ms when counter values run out, with no limit. The server can't check `count` against the data, and section 3's rejection list allows `len = 0` with `count = 65,535`, so 32 bytes buys about 1 ms. One 2,097,184-byte publish of 65,537 such records moves a stream about 65.5 s ahead, 1,000 of them about 18.2 hours, and sustained 1 GB/s about 8.7 hours per second. Every later record on that stream, from any producer, then gets a future timestamp until the clock catches up. Order stays strict, so this isn't an ordering bug. By reading only, since those layers aren't built: id-range time filters, retention by ingest time (section 7.4) and `sealed/<ingest_hour>` paths would use the skewed time, and under Q6/D15 the highest id at takeover raises the floor for every stream on the node, so one publisher could skew other streams after a restart. Rejecting `len = 0` with `count > 1` only raises the price, since a few data bytes pass, and it would contradict the `max_count.hex` vector. Options: reject a publish that would put ids more than a set margin ahead of the clock (error 8, or backpressure), or limit items per second per stream. Assumption: no bound, because adding one is a new mechanism and the margin is a product choice. **Not fixed.** `q13_empty_max_count_records_move_ids_ahead_of_the_clock_without_bound` in `crates/format/tests/ids.rs` pins the behaviour and changes with the decision.
- **Q10. Conditional update on the ownership record.** "One ownership record" with a conditional increment needs compare-and-swap, which `object_store`'s `LocalFileSystem` doesn't implement (`PutMode::Update` returns `NotImplemented`; checked in 0.11.2). Assumption: D14.
- **Q14. A stream id ending in `*` can't be granted exactly.** Section 1 allows any UTF-8 name without `/`, so `team*` is a legal id, but a trailing `*` in a pattern is always a wildcard (D25, D46) and a pattern has no literal form. An issuer granting exactly `team*`, or building `inbox.<user>` from a user-chosen name of `*`, also grants `teamsecret` or every `inbox.` stream, with no error at sign or verify. That widens access against section 12's "anything private goes in its own stream". Options: forbid a trailing `*` in stream ids (narrows section 1), or add an escape to patterns (a new mechanism and a token format change). Until then an issuer that builds patterns from user input must refuse a trailing `*` itself. Assumption: no change, because both options change the spec's meaning. **Not fixed.** `q14_a_grant_on_a_stream_id_ending_in_star_is_a_prefix_grant` in `crates/auth/tests/token.rs` pins the behaviour and changes with the decision.
- **Q15. Bit rot in a closed WAL file can't be told from its normal end.** A closed file ends in zeros or in stale entries of a reused file, and a corrupt entry looks the same, so replay takes each file's valid prefix and goes on to the next (D8 has no end marker). A flipped bit in the middle of a closed, not yet recycled file silently drops that file's later entries, while later files replay, which can leave a gap inside a stream. A torn tail in the active file, the case the CRC is for, is unaffected. Options: a final entry marking a clean close, or the closed length in the next file's header, both new mechanisms. Assumption: leave it, since a closed file is needed only if the machine crashes before its segment is uploaded. **Not fixed.** `a_directory_replays_oldest_first_and_ignores_other_files` covers the walk, and no test claims detection.
- **Q16. Object paths can collide.** Section 7.3's path holds `<node-or-stream>`, so a stream named like the node shares a directory with it, and `first_id` isn't unique across streams, so two objects can in principle want one path, most easily with ids borrowed ahead (Q13). Assumption: the uploader never overwrites. Identical bytes count as done, and different bytes fail that upload and hand its references back (D55), which is safe but leaves those records unuploaded until someone acts. Options: reserve a prefix for one of the two, or add something unique to the file name. Please choose.
- **Q17. A per-object failure the uploader can't recognise still stalls it.** D59 fails an upload whose path can't exist, or whose store error says retrying is pointless. Every other error retries forever on the one thread (D55), because it can't be told from an outage: `LocalFileSystem` reports most I/O failures as `Generic`, and real S3 was not exercised, so its responses aren't known. If some store rejected one object deterministically with such an error, every later upload on the node would wait behind it. Options: move retries off the head of the queue (needs its own bound to keep backpressure), or cap attempts (can't be told from a long outage). Assumption: leave it, since no such case is known. **Not fixed.**
- **Q20. Can a snapshot show state that isn't durable yet?** Section 10 says a change "goes into the WAL, is applied in RAM, and is then acked", and section 5.2 holds delivery until the WAL, but says nothing of a snapshot. `expect_ver` has to see earlier changes as soon as they are stamped, so they are applied at once, and a snapshot taken during the fsync can return a version that a crash then erases. A lease holder could see a version that later doesn't exist. Options: a snapshot waits until the stream's last ticket is durable (it would hang on a held WAL, and the snapshot would be slower), or leave it. Assumption: it doesn't wait. **Not fixed.**
- **Q21. What does a stream's own record of moves cost over time?** A stream carries `(last_id, core)` per move, so a retry can find the core that stamped it (D67), and each core keeps its override entries and old shard locations for good (D66). Nothing trims them. Moves are few, so this is small, but it's unbounded on a node that lives long and rebalances often. M7's metadata is the natural place to prune history older than the sealed extent. Assumption: leave it for M7. **Not fixed.**
- **Q18. Who enforces the segment size cap?** Now assumed answered by D64: each core asks for a seal at its share. Please confirm.
  Original question:  Section 7.3 writes a segment every seal window "or earlier when the size cap is reached (32–128 MB)". Nothing enforces or names a cap: `build_seal` and `SegmentBuilder` accept any size, and `docs/BENCH.md` records a 1,000,000-stream object of 221 MiB. One object per seal is built from sections sent by N independent cores, so no core can see the object's total, and the uploader only sees it after every core has sealed, too late to seal "earlier". Options: each core seals early on its own share of the cap and tells the others by message, as part of M4's seal logic; or the uploader splits a completed seal into several objects, which breaks one PUT per seal and only bounds the object, not the window. Assumption: M4 owns this (noted in its scope in `docs/BUILD_PLAN.md`), and until then there is no cap. **Not fixed**, and there is no regression test, because what to test depends on the choice.
- **Q19. Nothing bounds a PUT while the uploader runs normally.** `shutdown` now abandons a PUT that doesn't return, but `finish`, and every upload behind a hung PUT, still wait for it. `build_store` sets no client timeouts, so S3 relies on `object_store`'s defaults, whose behaviour in an outage wasn't measured because real S3 was not exercised. A stalled `LocalFileSystem` mount has no bound at all. Options: a per-attempt timeout that counts as a retryable failure; its value is a product choice, and for large objects it must allow for the upload's length. Assumption: no timeout. **Not fixed.**

## Decisions

### Format and frames

- **D1.** `op` in filter clauses: 0 = `eq`, 1 = `any`. Reason: the spec gives the field but no codes.
- **D2.** `nfilt = 0` matches every record; `nfilt > 4` is error 8. Reason: follows "up to 4 clauses".
- **D3.** App filters (`options`, `author`) don't apply to system records; `INCLUDE_SYSTEM` delivers them all. Block skipping for such a reader is allowed only when the block's `author` is a non-zero value. Reason: on system records `options` is the entry type, so a block could otherwise be skipped while holding one.
- **D4.** `SDK from`: the client sends `from = head` after a snapshot. Reason: section 10 says "read from `head + 1`", and section 5.1 defines `from` as "after this id", so they agree only this way.
- **D5.** A publish with `HAS_STATE` places the system record last. `ACK.first_id` is the first id of the publish and `ACK.count` counts all its items, including the system record. Reason: `first_id + i` then still maps to the producer's items.
- **D6.** `producer_id = 0` means no idempotency: it is what `STATE_OP` and HTTP publishes without the headers use, and it creates no dedupe entry. Reason: the WAL entry always has the field, and `expect_ver` covers state retries.
- **D6a.** Level 0 sends no `ACK`, but a rejection still gets a `NACK`. A publish below a stream's minimum ack level is raised to it. A publish with neither records nor state is error 8. A state result over 64 KB is error 8. Reason: smallest reading of sections 3 and 13.
- **D6b.** `STATE_RESULT` carries `ok = 0` only for a version conflict; other failures send `ERROR` with `ref = req`. Reason: `STATE_RESULT` has no code field.
- **D6c.** Merge is RFC 7396 semantics on CBOR maps. Incr's doc is CBOR `{"path": [keys], "n": int}`. Incr on a non-numeric value is error 8. Reason: the spec names the ops but not incr's doc.
- **D6d.** Defaults: `max_frame` 16 MiB, subscriptions per connection 1,024, subscriber queue 8 MiB, `PROGRESS` every 5 s, slab 4 MiB, block 64 KiB, footer page 64 KiB. Reason: plain starting values; all are constants or node config.
- **D6e.** Dedupe's 28 bytes are `producer_id, producer_seq, first_id, count`, and idle age comes from `first_id`'s timestamp. Reason: the id already holds the time, so no field is added.
- **D33.** An `eq` clause with `value & !mask != 0` matches nothing, and its block decision is "none match". Reason: keeps sections 4 and 4.1 consistent (Q11).
- **D34.** A publish with more than `u32::MAX` items is rejected with error 8. Reason: `ACK.count` couldn't report it (Q12).
- **D35.** A block summary's `count` is items, and `bytes` is whole records including headers and padding. The summary's on-disk layout is left to M3 (D10). Reason: the spec names the fields only; items match the id range, and whole-record bytes are what a reader fetches.
- **D36.** The allocator never issues `u64::MAX` and refuses an allocation that would need it. Id 0 is never issued either. A clock above 48 bits is clamped. Reason: section 5.1 gives both values cursor meanings, and `first_id = 0` means "already committed" in an `ACK`.
- **D37.** A record overlapping a filter's id range matches whole, and the decoder rejects non-zero padding as well as validation does. Reason: section 5.2 sends whole records; padding isn't data, and nothing valid has non-zero padding.
- **D38.** `validate_forward` requires a non-zero `author`, and `id = 0`, for records from a forward sink. Reason: section 3 lets forward sinks set `author`, and D28 keeps system records out.
- **D39.** Frame decoders are strict: unknown types, undefined flag bits (flags must be 0 on frames that define none), trailing bytes, `ack` above 3, a state `op` outside 1–3, `ok` above 1 and error codes outside 1–8 are errors. Reason: each frame then has one encoding, and section 3 and 11.1 define no other values.
- **D40.** A token's text form is the lowercase hex of D25's bytes. Reason: `HELLO` carries `token str`, which must be UTF-8, and a Bearer header must be text, but D25's bytes are binary; hex needs no dependency, and one case means one text form.
- **D41.** `HELLO.ver` is 1 for now, and the codec doesn't check it. Reason: the spec gives the field but no value, and what to do on a mismatch belongs to the connection (M6).
- **D42.** A stream id in a frame must be non-empty as well as free of `/`, and the codec checks both. Reason: section 1 calls them names; a bad id fails as error 8 before reaching a core.
- **D43.** `max_frame` covers the whole frame, including `type` and `flags`. A frame above it is error 6, and every other decode failure is error 8. Reason: the WebSocket message length is what a reader can check first.
- **D44.** The codec accepts all 32 `SUBSCRIBE` flag combinations, including `WITH_STATE` with `STATE_ONLY`, and leaves their meaning to the subscribe handler (M5). It also doesn't check `sink:*` cursor names (D27), state doc size or CBOR, or record validity, which belong to the owner. Reason: these need context or are section 3's validation, and the codec never reads inside `records`.
- **D45.** Permission bits: `read` 0x01, `publish` 0x02, `state` 0x04, `admin` 0x08, and other bits make a token invalid. Reason: D25 gives `perms u8` but no bits.
- **D46.** A token is expired once `now_ms >= expiry_ms`. `*` is a wildcard only as a pattern's last character, and it matches an empty remainder, so `logs.*` matches `logs.` but neither `logs` nor `logsx`. A `*` elsewhere is an ordinary character. The signature is checked before the body is parsed. Reason: smallest reading of D25; unauthenticated bytes never reach the parser.
- **D47.** `Token::sign` and `verify` accept any secret length, including empty. Rejecting a weak secret is for node config, when it is added (M6). Reason: the token code has no policy on keys, and HMAC accepts any length.
- **D48.** Token text is at most 65,535 bytes, so 65,534 in practice because hex is even, and `body | signature` at most 32,767 bytes. `sign` and `verify` both return `TooLong` above it, on HTTP as well. An exact grant on a stream id over about 32.7 KB can't be issued, though such an id is valid (section 11), and has to use a shorter `*` pattern. Reason: `HELLO` carries the token as a `str`, and one limit means a token can't work on HTTP and always fail on WebSocket.
- **D49.** The `auth` crate is `no_std` plus `alloc`. A test refuses any opt back in to `std` in any `.rs` file under `src/` at any depth, source pulled in with `path` or `include`, a build script, and any manifest line outside a short allow list, which covers target-specific and table-form dependencies. Reason: it makes "verification does no I/O" a compile error instead of a source search that a nested import gets past. The check is a word scan, not a parser, so it is meant to catch mistakes and not a determined author; the two hash crates and their workspace entries are trusted.

### Storage

- **D7.** A core keeps a bounded outbound queue for when `try_send` fails and stops reading publish frames while it is non-empty or the memory cap is reached. Reason: backpressure without blocking a core or dropping a stamped record.
- **D8.** The WAL is a sequence of preallocated files, `wal-<seq>.log`, with one active at a time, rotated at seal, and renamed for reuse once its segment and checkpoint are durable. The first 16 bytes of each file are a magic and `seq`, and the entry CRC is seeded with `seq`. Reason: stale entries in a reused file fail the CRC, with no added entry field. The CRC isn't enough on its own, because it isn't authenticated: see D60.
- **D9.** WAL entry: `stream_len u16 | stream | producer_id u64 | producer_seq u64 | len u32 | crc32c u32`, then the record bytes padded to 8. One publish is one entry, so an atomic publish can't be torn apart. State ops are found by reading `author = 0` records during replay. Reason: the spec's fields in its order.
- **D10.** Segment layout: sections of stream extents, then footer pages sorted by `xxh3_64(stream)`, then the top index and a fixed trailer (`magic, top_offset, top_len, crc32c`). Each extent starts with a block summary table followed by blocks of whole records. Stream index entries hold the full name to resolve hash collisions. Reason: follows section 7.3; a reader's data step may take one read for the table and one for the blocks.
- **D11.** Unsealed records are served from memory, since slabs are pinned until upload. The local tier is a copy of the uploaded segment, under a byte cap. Reason: the WAL is read only during recovery.
- **D12.** The uploader is one thread with its own current-thread tokio runtime, used only for `object_store` calls. Reason: `object_store` is async, and the thread pattern is the spec's.
- **D13.** Extra node config beyond section 13: listen address, TLS cert and key, token secret, object store URL and credentials source, node name, `data_dir` (KV and local cache), local cache cap, memory cap, and `sink_allow_private_addresses` (default false). Reason: required to run; none changes behaviour the spec defines.
- **D50.** Every WAL entry starts at a multiple of 8 in its file, so the padding of D9 brings the whole entry, not just the records, to a multiple of 8. The CRC covers every entry byte except itself, padding included, and is seeded with `seq`. `stream_len = 0` and `len = 0` are invalid, which is what ends the prefix at a preallocated tail of zeros. Reason: padding is part of the entry, and no publish has an empty id or no records (D6a, D42).
- **D51.** Preallocation is `set_len`, which is sparse on APFS and on Linux filesystems. A write past the preallocated size just extends the file. Reused files keep their size (D60). Reason: real allocation needs `fallocate` or `F_PREALLOCATE`, so `unsafe` or a libc dependency, for a benefit nothing here has measured. A file's writes therefore may still allocate, and `sync_data` then also flushes that metadata.
- **D52.** Segment bytes are documented at the top of `crates/storage/src/segment_format.rs`. Three choices beyond D10. (1) A footer page's 64 KiB is a target, not an exact size, and pages aren't padded: a page holds all entries with one hash, however many, so a lookup is always one page read, and a stream id can be longer than a page. (2) A block is at most 64 KiB unless a single record is bigger. (3) The trailer has no fixed place for a reader to find the top index without knowing the object's size, so the first read is a 256 KiB suffix read, which holds the trailer and normally the whole top index (about 11,000 pages). A bigger top index takes a second read, and is tested. Reason: one read and no `HEAD`.
- **D53.** `ingest_hour` in an object path is whole hours since the epoch, from the object's lowest id. Generation and `first_id` are zero-padded to 20 digits. Each is one path part, so `object_store` encodes anything unsafe in a stream id. Reason: the spec names the parts but no form, and padded numbers list in order.
- **D54.** The local cache is one directory laid out as `LocalFileSystem` expects, so `SegmentReader` reads it as a store, and is owned by the uploader thread. Reads happen on cores through the file system, and tell the owner with a `try_send` that may be lost, on a queue of their own, so reads can't make a section come back `Full` and turn into publisher backpressure. Eviction is least recently used by bytes, and after a restart by modified time. Writes aren't fsynced. A failed write removes its temp file, and eviction removes directories it empties, as does opening. Reason: no lock is shared, CRCs catch a bad copy, and a miss falls through to S3.
- **D55.** A seal or dedicated object is written with one plain `PUT` using `PutMode::Create`, so S3 needs `S3ConditionalPut::ETagMatch`, which `build_store` sets. If the path already exists with the same bytes, an earlier attempt succeeded and its response was lost, so it counts as done. With different bytes the upload fails (Q16). Store errors retry forever with exponential backoff, keeping the references, except those in D59. `shutdown` stops retrying, abandons a PUT in progress and returns every reference as `UnfinishedUpload`. An abandoned PUT may still land, which is harmless: the same bytes count as done if uploaded again, and an object no extent refers to is ignored (D16). A PUT stuck on a blocking thread keeps that thread until the call returns, since it can't be cancelled; the thread ends with the process. A section from a core out of range, or with a seal number not above that core's last one, fails and comes back the same way, so a repeat is caught after its seal has uploaded too, and a seal gets one PUT. A core's seal numbers must therefore only go up. Reason: never lose a reference or overwrite a sealed object. Retrying forever is Q9's assumption.
- **D56.** A WAL entry carries the owner's `core` and a per-core `ticket`, and the writer reports each core's highest durable ticket through a `tokio::sync::watch`, which an awaiting core wakes on. `changed()` failing means the writer stopped. `records` is generic over `AsRef<[u8]>`, and so are the uploader's references, so that M4's slab references plug in with no copy. Rotation goes through the same channel as appends and returns `{closed_seq, new_seq}`, so for M4's seal: rotate first, then each core seals what it holds once it hears the result. Everything in a closed file was sent before that, and so is in some core's section, which makes `try_recycle(closed_seq)` safe once that seal's segment and checkpoint are durable (D16). A group is capped at the channel's capacity, so fast senders can't hold one group open. Reason: the smallest message set that lets the cores keep everything else.
- **D57.** `MetadataStore` keys and values are opaque bytes, and `apply` commits atomically and persists with `SyncData`. What a stream's metadata holds is M7's (section 7.6). A key must be 1 to 65,535 bytes (Fjall's limit) and a value at most 2^32 - 1 bytes; anything else returns `MetadataError` before anything is applied, and a longer prefix scans as nothing. A stream id may itself be 65,535 bytes (section 11.1), so M7 can't simply add a prefix to one: such a stream would get the error. Reason: the fields' encoding has no user before M7, and Fjall panics on these inputs.
- **D58.** The uploader's channel and the dedicated-object decision: a core decides when a stream has filled its buffer and calls `try_send_dedicated`, because the buffer belongs to the core (M4). Each core sends one section per seal, empty if it has nothing, so the uploader knows when a seal is complete. A seal with no records writes nothing and reports `Empty`. Reason: section 6.4 has per-core hand-offs and one PUT per seal, which needs a count.
- **D59.** A path part may be at most 255 bytes as encoded (`MAX_PATH_PART_BYTES`), on every store, and a stream id that exceeds it can't have a dedicated object. The uploader reports `Failed` without trying, and keeps the references as in D55, so later uploads aren't held up. A core must check `stream_fits_dedicated_path` and keep such a stream in its seal sections, where the id is only in the footer and any length works, so section 1 still has no length limit. A node name over the limit fails every seal the same way. `InvalidPath`, `NotSupported` and `NotImplemented` store errors also fail at once rather than retrying (D55 still retries everything else; see Q17). Reason: 255 is the file name limit of common file systems, and one limit means a stream behaves the same on S3 as in a local test.
- **D60.** Reusing a WAL file empties it first: `set_len(0)` and `sync_all` under the old name, then the rename, then `set_len` back to its old size and the header. Entries in a closed file are already uploaded (D16), so nothing is lost at any crash point, and an empty file replays as no entries. Reason: record data is written verbatim and a seeded CRC isn't authenticated, so a publisher could plant a valid entry for a predictable future `seq`, with any stream, ids and `author = 0`, and replay would walk into it if new entries ended at that offset. Nothing at the entry level can reject those bytes, so they must not exist. An unpredictable per-file seed would stop guessing but change the file format, and writing zeros is O(file size) for the same result. Cost: a reused file no longer has allocated blocks, so its writes allocate as a new file's do (D51), and reuse now saves little beyond the create. Not measured: `wal_throughput` doesn't rotate, so docs/BENCH.md's numbers aren't affected. If reuse turns out not to be worth keeping, removing it is a separate choice.
- **D61.** Every uploader send is `sending_count += 1`, a check of the stop flag, the `try_send`, then `sending_count -= 1`, all sequentially consistent. After a stop, the uploader thread sees the count reach 0 and only then drains the channel. Reason: a command accepted with `Ok` while the thread was finishing was otherwise dropped with the receiver, against D55, and a sender that never paused kept the drain from ending. Sends happen per seal, not per record, so these shared atomics are off the hot path, and no sender ever waits. Only the uploader thread waits, for the length of one `try_send`.
- **D62.** A core retries a full WAL or uploader channel on a 1 ms timer while something is waiting. Reason: crossbeam gives nothing to await, and the writer's wake-ups only cover the core's own entries, while the channel can be full of other cores' entries.
- **D63.** An atomic publish or state op copies the stamped records and system record into one new slab region of the owning core, since one WAL entry holds one reference. A plain publish is never copied after it is read. Reason: the doc comes before the records on the wire, so the frame can't hold the system record where it belongs without the frame reader knowing; the cost falls only on publishes with state.
- **D64.** Each core sends the control thread a seal request when its unsealed bytes reach `segment_cap_bytes / core_count` (default 64 MiB, the middle of section 7.3's range), and one seal starts for the node (Q18). The bound is soft: bytes arriving before the seal reaches a core land in it, and one busy core seals at its share, not at the total. Reason: a core can't see the others' bytes, and this keeps one PUT per seal.
- **D65.** A publish carries no route. A core that doesn't own the stream forwards it, and tells the client `Moved`. The client keeps its route per stream until a barrier sent down the old route comes back from the owner (`RouteDone`), and only then sends directly. Forwarded writes use an unbounded inbox, so two cores forwarding to each other can't wait on each other; what is in it has already been read from a bounded inbox. Reason: a publish sent on the new route could otherwise overtake one still being forwarded, and the older one would look like a duplicate and be dropped. No core or client needs a current routing table for this to be correct.
- **D66.** Each core's own map of `shard → where it last knew it was` is enough to reach an owner, because every core that gives a shard away remembers where it went. A stream's override entry is kept by every core that has owned its shard or its own shard, and a hashed shard's owner passes on entries for streams that hash to it. A handoff's location for an override shard is taken only by a core with no entry for that shard. A core's own entry stays, since it may have held the shard since the sender last heard. So each hop leads to a later holder of the shard, and the walk can't cycle or make a second owner. The control thread alone has the complete table, updated when a move finishes. Reason: a core acts only on what messages told it, with no shared table.
- **D67.** A retry waits for what it duplicates to reach the level it asks for. An older retry waits on the producer's latest publish, which came after it. If another core stamped those ids, it gets the wait as a message, using the `(last_id, core)` list the stream carries. A batch no longer held counts as uploaded. Reason: section 3 says the original `ACK`, and invariant 3 says never before the level is met.
- **D68.** A stream's unsealed batches and the acks waiting on them stay on the core that stamped them when it moves: its section covers them, which is how the seal gets its two footer entries. A seal takes one stay on a core per stream, so that a stream moving away and back in one window can't produce an extent overlapping another core's. The later stay waits for the next seal. `read_memory` reads one core's batches only, so reading a stream just after a move has to go to both, and that is M5's to build.
- **D69.** Level 3 acks when the object holding the batch is uploaded, and doesn't also wait for its fsync: an entry sent between the rotation and the core hearing about it can reach the store first, and then S3 holds it, which is stronger. A seal takes only batches the WAL channel has accepted, so nothing reaches S3 ahead of an entry still queued on the core. An upload that fails for good (D55, D59) leaves its level 3 acks unsent, and is counted in `CoreStats`.
- **D70.** `STATE_OP` has no `ack` field, so it uses the stream's default level, with level 0 treated as 1 since a result has to go back. Reason: section 10 acks after the WAL by default, and `STATE_RESULT` has to answer.
- **D71.** A rejected publish creates no stream. A stream is created when a publish or state write is accepted, or by `configure`. An id space exhausted on a new stream (only possible with a floor near `u64::MAX`) leaves it empty. A snapshot of a missing stream is error 2.
- **D72.** Node defaults: 4,096 virtual shards, 64 override shards, a dedicated object at 32 MiB unsealed, an overload ratio of 1.25 × the mean, 16 moves per check, a check every 10 s, 1,024 writes per inbox. A shard's load is its ingest, fan-out and catch-up bytes as moving averages with weight 0.5 per check; subscribers are counted but not weighed. A move takes the largest shard smaller than the gap to the coldest core, so a single huge shard stays put, and it takes the override table to split it. Fan-out, subscriber and catch-up counters have no source until M5. Reason: plain starting values.
- **D73.** The memory cap (D7) is checked in `Client::publish`, as the analogue of a connection not reading its socket, against the slabs of the client's home core. A core's own copies (D63) aren't limited by it. It should sit well above the segment cap, or nothing would free memory until the window ends. Reason: section 6.5's regions belong to the pool they were read into, wherever their stream lives (D24).
- **D74.** `SlabBytes` holds a `Bytes` and an `Arc` to its tracker, so one reference change is two atomic operations: per batch, but two. The tracker is what knows the slab's size and when it has gone. Regions come from one `BytesMut` split apart, so there is no `unsafe`, and the server crate forbids it. Slab memory is never recycled: a new slab is a new zeroed allocation. Reason: one count per slab with an in-place write would take `unsafe` for a saving nothing has measured.
- **D75.** Replay-based recovery, WAL recycling and checkpoints wait for M7: nothing here calls `try_recycle`, so WAL files accumulate until then, because D16 needs a checkpoint first. Each node starts at generation and `last_valid_id` from config, and an uploaded object is only reported, not yet recorded as an extent.
- **D76.** An `incr` path is limited to 256 keys, the depth the CBOR parser accepts, and refused before anything is built. The result of every `merge` and `incr` is parsed again before it is accepted, and anything it can't read is error 8 with nothing changed. Reason: section 3's validation bounds a doc's size and form, but a flat `path` turns into nesting only when applied, so a long one overflowed the core's stack and aborted the node, and a shorter one committed state that no later merge, incr or replay could read. A re-parse is the one check that can't disagree with the parser, and costs one parse per merge or incr (docs/BENCH.md).

### Recovery

- **D14.** Ownership is stored as `ownership/<generation>` created with `PutMode::Create`; the highest generation is current. Each holds the previous generation's last valid id. Reason: the same conditional write works on S3 and `LocalFileSystem`, and a losing process sees a clean failure.
- **D15.** Id assignment is `max(last_id + 1, now_ms << 16, last_valid_id + 1)`. Reason: new ids stay above everything a former owner could have issued.
- **D16.** The WAL is recycled only after both the segment and its checkpoint are durable, and replay skips ids at or below the stream's sealed extent. An uploaded object with no extent is ignored and ages out. Reason: a crash between steps neither loses nor doubles records.
- **D17.** Compaction applies the last valid id too, and drops an older generation's records above it. Reason: compaction must not resurrect what readers would ignore.
- **D18.** Checkpoint files are `checkpoints/<generation>-<seq>.ckpt`, in the same paged footer format. A lookup walks newest to oldest using cached top indexes, and a periodic full checkpoint removes the need for older files, which are then deleted. Reason: the simplest way to bound the walk (Q8).
- **D19.** Fjall with default features off. Reason: pure Rust, and its default `lz4` feature would break the no-codec rule.
- **D20.** Deleting a stream writes a tombstone to the local store and checkpoint, and its old records stop being reachable and age out with their prefixes. Reason: rebuild must not resurrect it, and "nothing else deletes data".

### API, auth and sinks

- **D21.** Admin routes, all under `admin` (Q2): `PUT` and `DELETE /v1/stream/<id>` (create or config, delete); `PUT`, `DELETE /v1/stream/<id>/sink/<sink_id>`; `POST .../sink/<sink_id>/pause`, `/resume`, and `/reset`. Bodies are JSON. Reason: the smallest set that reaches what the spec already requires.
- **D22.** WebSocket and HTTP share one TLS 1.3 port, with the upgrade at `/v1/ws`. Reason: one listener.
- **D23.** The server has its own small RFC 6455 frame reader, tested against `tokio-tungstenite`. Reason: existing libraries read into their own buffers, and section 6.5 needs frames read into slabs and unmasked in place.
- **D24.** Connections are accepted once and handed to cores round robin. Bytes read on a non-owner core reach the owner as an exclusive slab region in a message, and are stamped there. Reason: a connection can use streams on several cores, and `SO_REUSEPORT` balancing isn't portable to macOS.
- **D25.** Tokens are `body | hmac_sha256(secret, body)`, with a little-endian binary body: `expiry_ms u64 | author u64 | n u16 | n × (pattern str | perms u8)`. Patterns match exactly or by a trailing `*`. A token with `author = 0` is invalid. Expiry is rechecked on every operation. Reason: verification needs no lookup, and HMAC is also what webhooks need.
- **D26.** HTTP: binary publish uses `Content-Type: application/x-sillystream-records`; any other type is the simple form. `filter=` is comma-separated `eq:<mask>:<value>`, `any:<mask>`, `author:<n>`. `PATCH state` takes the op in `X-State-Op`. Results for publish and state are small JSON objects; reads are binary. Reason: the spec names these but gives no encoding.
- **D27.** `sink_id` is a `u64`, and clients may not create cursors named `sink:*` (error 8). Reason: `forward` uses it as `producer_id`.
- **D28.** Sinks never forward or deliver system records. Reason: forwarding `author = 0` would inject state ops into the target.
- **D29.** `webhook.deliver` posts the record bytes unchanged, with `X-Sink-Id`, `X-First-Id`, `X-Last-Id` and `X-Signature` (HMAC-SHA256 over the body). The resolved address is what gets checked against private ranges. Reason: fixes the spec's fields to a form, and blocks DNS tricks.
- **D30.** A sink's skip gap is logged and shown in the stream info. Reason: the spec says "records the gap" without a place.
- **D31.** A stream's retention is read at compaction time; changing class affects data from that point on. Reason: compaction copies forward and nothing rewrites old prefixes.
- **D32.** Test hooks are behind a `test-hooks` cargo feature of the server binary: a clock offset and named crash points. Reason: retention and crash windows can't otherwise be reached end to end, and release builds must not contain them.

## Known test gaps

**Mutation testing: several storage behaviours can be broken with every test still green. Not fixed.** The production code is correct in each case; the tests don't hold it there. Each mutation was a one-line change of `crates/storage/src`, run against the relevant test binaries, at commit e5e598c.

1. `segment_builder`: `id_last = header.last_id()` changed to `header.id` survives the segment and uploader tests. No test checks an extent's `id_last` for a record with `count > 1`, so the id range in the stream index, which readers rely on, is unguarded, and the overlap check is weaker for multi-item records.
2. `segment_reader`: removing `extents.sort_by_key(|e| e.id_first)` from `read_stream` survives, because `a_stream_in_two_sections_returns_both_entries` only adds the early section first. A stream moving from a higher core to a lower one isn't tested.
3. `wal_writer`: removing `.take(self.channel_capacity)` survives, so D56's claim that a group is capped has no test.
4. `segment_reader`: removing the "table doesn't add up to the extent" check survives.
5. `segment_format`: removing the "page is past the top index" check survives, because `decoders_refuse_nonsense_that_has_a_valid_crc` doesn't reach it.
6. `uploader`: removing the backoff doubling survives, so exponential backoff and `retry_max_ms` are untested.
7. `metadata`: removing `persist(PersistMode::SyncData)` survives, so "durable before returning" isn't tested. There is no crash or sync injection.

Separately, the temp file cleanup in `SegmentCache::put` is tested through a failed rename only. A failed `write_all`, as on a full disk, wasn't injected. It takes the same cleanup path.

**M4: what the tests don't reach.** Tests run real threads against a scripted WAL file and store, with an injected clock for ids and dedupe. Thread scheduling isn't scripted, so shard moves are checked under real races and not replayed deterministically, and no crash test exists until M7. The rebalancer's timer runs on real time. No test injects a full uploader channel into a seal (the retry path is the same one as the WAL's), or a move while a WAL channel is full.

## Process

- **The shared `CARGO_TARGET_DIR` can give false results during concurrent runs. Not fixed.** A review run saw `more_than_four_clauses_is_rejected` panic at `crates/proto/src/client.rs:293:27` (`slots[..nfilt]`), which the guard just above it rules out in the unmodified source. The same test passed on rerun and in a private target dir. The cause is inferred, not proven: agents building mutated copies of this workspace may reuse artifacts in the shared directory. It depends on timing and wasn't reproduced. While other agents are building, a red or green result from the shared target may not reflect the source, so confirm a surprising result in a private target dir before trusting it. No code change addresses this, since the source is correct; the remedy is not to run mutation builds against the shared target.
